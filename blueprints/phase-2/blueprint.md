This blueprint is **additive**. It never rewrites Phase 1 code except where a delta below names the

## 1. Project Overview & Non-Goals

### Vision

Phase 1 shipped the portfolio, blog, CMS and hardened deploy. Phase 2 raises the site's *reach* and
*credibility* without changing what a returning visitor sees by default: shareable content with
working preview cards, admin-managed special-event themes, a desktop-style menu, real PDF export,
project delivery metrics, a second "Life / Gaming" blog gated behind the Matrix theme, a downloadable
"Tools" section with first-party download analytics, a self-hosted analytics dashboard, admin-editable
SMTP, a terminal command widget, grouped social profiles, a www/apex canonicalisation fix, and
visitor-submitted testimonials that the owner approves one by one.

The single governance change: Phase 1 auto-promoted a merged PR to production. Phase 2 inserts a
**sponsor review & approval gate on `staging.miautrix.tech` before every production promote**. No
merged change reaches production until the owner has reviewed it on staging and said go.

### Current state

- **Themes:** two hardcoded — `technical` (default, the user-facing label is "Console") and `matrix`.
  `ResolveTheme` middleware trusts only the literal string `matrix` from the `miautrix_theme` cookie;
  CSS token blocks keyed by `[data-theme="…"]` live in `resources/css/app.css`; the switcher POSTs to
  `/theme` (`ThemeController`, `Rule::in(['technical','matrix'])`). Page cache key is
  `public-page:{theme}:{path}`.
- **Blog:** one `Article` model + `ArticleObserver` (busts cache on publish/unpublish/delete via
  `InvalidatePublicPageCache::forArticle`), `ArticlePolicy`, Filament `ArticleResource`, `/blog` +
  `/blog/{slug}` inside the `cache.public` group, plus `/feed.xml`. `Article::scopePublished()` gates
  on `published_at` (not the `published` boolean).
- **Social profiles:** `SocialProfile` belongs to `Profile`; has `show_in_footer` + `icon_media_id`;
  rendered in the footer (`<x-footer-social-profiles>` class component) and on `/connect`
  (`ConnectController`) as one flat list.
- **Contact:** `ContactForm` Livewire component → `ContactMessageMail`, sent synchronously,
  rate-limited 5/hour/IP, honeypot. SMTP is `.env`-only (`MAIL_*`).
- **OG images:** `App\Support\Seo\OgImage::resolve(?int $mediaId)` returns `route('media.show', …)`
  or `asset('images/og-default.png')`. Social crawlers currently render a blank card — root cause
  unconfirmed (Cloudflare bot filtering, non-absolute URL, stale `cache.public` HTML, or `media.show`
  404ing for unauthenticated crawlers).
- **Projects:** `Project` model, `documents` many-to-many (renders a "Documents" section), a
  `project_media` gallery, a Filament `RichEditor` description.
- **Middleware:** global `SecurityHeaders` (per-route CSP — `$request->is('admin*')` gets `PANEL_CSP`
  with `'unsafe-eval' 'unsafe-inline'`; public gets `PUBLIC_CSP` with `script-src 'self' 'unsafe-eval'`
  and `style-src 'self' 'nonce-<per-request>'` via `Vite::useCspNonce()`). `Permissions-Policy`
  currently sends `geolocation=()`. `cache.public` alias wraps content routes. `ResolveTheme` shares
  `$theme`. No `RecordPageView` middleware exists. `trustProxies(at: '*')` is set.
- **No task scheduler** is wired (`routes/console.php` has only `inspire`). Production runs a
  supervised `queue:work` (database driver). No Redis anywhere.
- **Test gate:** `composer test` = `pint --test` → `phpstan analyse` → `pest`. The CI check-run is
  literally named `ci` and branch protection depends on that exact name. Node 24.20, PHP 8.4 in CI,
  Postgres 18 service container. Local Pest points at a network Postgres (`miautrix_test`, currently
  17.11 — an accepted deviation); `docker-compose.yml` `postgres:18.6` on port 5433 is the fallback.
- **Deploy:** `bash infra/deploy.sh` — build-machine gate → SSH → server pulls from GitHub,
  `migrate --force` expand-only, atomic symlink cutover, `cache:clear`, supervisor + fpm reload.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|
| The administrator (site owner / **sponsor**) | Manage themes, tools, testimonials, SMTP, and analytics via Filament; review each Phase-2 change on staging and approve production promotes | Weekly, more during a release |
| Recruiter / hiring manager | Read projects with delivery metrics, download a project or article as PDF, download a tool, browse grouped social links | Once, occasionally revisits |

| Casual visitor | Play with the terminal widget, run `whoami`, share a post | Once |

### Goals — Phase 2 scope

1. The product lets a visitor share any blog (and later Life) post to six networks with a working
   preview card, and records each share click first-party.
2. The product lets the administrator create date-windowed special-event themes in Filament, beyond
   the fixed `technical`/`matrix` pair, with the visitor switcher offering only currently-active ones.
3. The product exports any project or article as a real downloadable PDF.
4. The product presents optional project delivery metrics (planned vs actual budget/schedule) as a
   stat strip and an "On time · On budget" badge.
5. The product serves a second "Life / Gaming" blog, visible only under themes whose
   `shows_life_blog` flag is set, with lazy click-to-play YouTube embeds under a `/life`-scoped CSP.
6. The product offers a "Tools" download section with per-download geo/referrer analytics and, for
   GitHub-linked tools, cached repo stats that render even when GitHub is unreachable.
7. The product shows a self-hosted analytics dashboard consolidating page views, share clicks, tool
   downloads and the professional-vs-Life traffic split — with no third-party tracker.
8. The product lets the administrator configure outbound SMTP in Filament (encrypted at rest) with a
   "send test email" action, overriding `.env` at runtime.
9. The product serves identical content and theme on `www.miautrix.tech` and `miautrix.tech`, with
   one canonical host and the other 301-redirected.
10. The product collects visitor testimonials the owner approves one at a time before they publish.
11. Every Phase-2 change flows implement → local gate → PR → CI (`ci`) → merge → **staging deploy →
    sponsor review & approval → production promote → live verify**.

### Non-Goals — explicitly out of scope for Phase 2

| Not building | Why not now | Revisit when |
|---|---|---|
| An RSS/JSON feed for the Life / Gaming blog | The professional blog's feed is the distribution channel; a personal-content feed invites syndication the owner does not want. `/feed.xml` stays professional-only. | The owner asks for a Life feed explicitly |
| MAC-address capture in `whoami` | Physically impossible for any web page to obtain a client MAC. Faking it would be a lie in a portfolio piece. | Never |
| Inbound mail retrieval (IMAP/POP3) for contact/testimonial replies | Phase 2 configures *sending* (SMTP) only. Archiving inbound replies is a separate feature nobody requested. | A concrete need to thread replies in-app |
| Identifying individual downloaders beyond IP-derived data | A tool download records IP-derived geo/ISP + UA only. Form-gating a download for identity is per-tool future scope. | A tool genuinely needs lead capture |
| A server task scheduler / cron for themes or GitHub stats | Themes evaluate at request time via `ThemeResolver`; GitHub stats refresh lazily on view with a 1-hour TTL and a stored-column fallback. Nothing needs `schedule:run`. | A feature genuinely needs periodic server work off the request path |
| HSTS preload-list submission | `SecurityHeaders` already emits the `preload` token; actually submitting to hstspreload.org is semi-irreversible and is the owner's deliberate call, not a build step. | The owner decides to submit |
| A Trusted Types CSP directive | Not introduced in Phase 1; Livewire/Filament/Alpine are not written against it. Out of scope. | The whole front end is audited for Trusted Types |
| Auto-deploy to production on merge | Replaced by the sponsor-approval gate — the defining governance change of Phase 2. | Never (this is the point of the phase) |
| Any rewrite of Phase-1 code not named in a §-delta | Phase 2 is additive. Touching un-named Phase-1 code is scope creep and a new way to break a frozen interface. | A delta names the file |
| A third+ hardcoded theme in `app.css` | Special-event themes are data rows (`themes` table) with JSON tokens injected at render — not new `[data-theme]` blocks. Only `technical` and `matrix` keep app.css blocks. | Never — the data-driven path is the design |

**The builder must not implement anything in this table**, even as a small addition while working on
an adjacent step. If a step appears to require a non-goal, that is a blueprint defect — stop and
report it rather than expanding scope.

## 2. Tech Stack

**No stack change.** Every framework, library and tool the repo already uses stays at its
`composer.lock` / `package-lock.json` version — refer to "the project's framework / ORM / test runner",
never a restated number. Phase 2 adds exactly **two** Composer packages, each installed by
`composer require` inside the task that first needs it (the repo's `composer.json` already exists, so
nothing is emitted under `workspace/`):

| Layer | Choice | Why this, over what |
|---|---|---|
| PDF generation | `barryvdh/laravel-dompdf` (new) | Pure-PHP PDF from a Blade view — no headless Chrome, no Node process, nothing new to run on the LXC. Rejected: `spatie/laravel-pdf` / Browsershot (needs Chromium on the server), `dompdf/dompdf` raw (the Laravel wrapper gives the facade + config the house style expects). |
| IP geolocation | `geoip2/geoip2` (new) | Reads a bundled MaxMind GeoLite2 `.mmdb` file locally — no per-request API call, no third-party runtime dependency (matches the "no third-party tracker" rule). Rejected: `torann/geoip` (heavier, wraps multiple providers), a hosted IP-geo API (adds a network call and a vendor to every download). |
| Special-event themes | `themes` table + JSON tokens injected at render | Data, not code. Rejected: a new `[data-theme]` block per event (unbounded app.css growth, a deploy per theme). |
| Terminal widget | Livewire component (already in stack) | Server-authoritative command handling, no new JS framework. |
| Nav menu / YouTube facade | Alpine.js (already bundled) + nonce'd inline handlers | No new front-end dependency; matches Phase 1's Livewire-on-Alpine model. |
| First-party analytics | `page_views` / `tool_downloads` / `share_clicks` tables + Filament widgets | Self-hosted, no tracker. Rejected: Plausible/Umami/GA (a third-party surface Non-Goal forbids). |

### Compatibility check

Checked against `knowledge/stack-compatibility.md` — no known-bad combinations. Specifically:
`barryvdh/laravel-dompdf` v3.1.2 requires PHP `^8.1` and `illuminate/support ^9|10|11|12|13.0` — the
repo's PHP `^8.3` (8.4 in CI) and Laravel 13 satisfy both. `geoip2/geoip2` v3.4.0 requires PHP `>=8.1` — satisfied.
Neither pulls a conflicting transitive (`barryvdh/laravel-dompdf` brings `dompdf/dompdf`;
`geoip2/geoip2` brings `maxmind-db/reader` + `maxmind/web-service-common`, all leaf libraries). No
Redis is introduced (queue/cache/session stay `database`). Filament 5 + Livewire 4 are untouched and
stay on the same major line, upgraded only together — Phase 2 changes neither.

**Boundary rules** (inherited from Phase 1's `CLAUDE.md`, restated for the new files)

- Controllers stay thin: find → authorize (Policy) → delegate to an Action or `Support/*` service →
  respond. `ShareRedirectController`, `ToolDownloadController`, `WhoamiController` etc. never build a
  query beyond a `find`/`firstWhere`.
- `app/Support/*` services (`ThemeResolver`, `GeoLocator`, `RepoStats`, `MailSettings`) never
  reference the HTTP request object or a Blade view — they take primitives and return primitives.
- Cache correctness is always Observer → `InvalidatePublicPageCache`. A resource class never busts a
  cache key directly.
- New Filament resources are `php artisan make:filament-resource <Model> --generate` then edited; the
  `Schemas/ Tables/ Pages/` split is mandatory. `MailSettings` and `Analytics` are **Pages**, not
  Resources.
- Every publishable-ish new entity (`Tool`) carries `slug`, `published`, `sort_order`, soft deletes,
  and every public query filters `published` + `deleted_at`.

**Resolution convention:** unchanged from Phase 1 — PHP via Composer PSR-4 (`App\` → `app/`), Blade
views via dot-notation against `resources/views/`. Artisan commands, Pest, and the running app all
load the one Composer autoloader; Vite/npm resolves JS separately with no naming overlap. See §19.6's
resolution convention matrix. No new import or link convention is introduced.

## 6. Frontend Architecture

Inherits Phase 1 wholesale: server-rendered Blade, one shared component tree, theme resolved
server-side before first byte, Livewire only where genuinely interactive. Phase 2 additions:

### New / changed routes (rendering)

| Route | Page | Data source | Rendering | Cache |
|---|---|---|---|---|
| `/life`, `/life/{slug}` | Life blog index/detail | `Article::life()->published()` | server Blade, theme-gated (404 when the active theme lacks `shows_life_blog`) | `cache.public`, key now host+theme-scoped |
| `/tools`, `/tools/{slug}` | Tools index/detail | `Tool::published()`, GitHub stats via `RepoStats` (lazy, cached 1h, column fallback) | server Blade | `cache.public` |

### Rendering strategy for the new surfaces

- **Life blog theme gate:** `LifeController` resolves the active theme via `ThemeResolver` and calls
  `abort(404)` when `shows_life_blog` is false. The nav entry for "Life" is hidden by the same
  condition in `<x-nav-menu>`. Because the page cache key already includes the theme, a `/life` entry
  cached under Matrix is never served to a `technical` visitor.
- **PDF routes** are registered **outside** the `cache.public` group (streamed binary) and return
  `Content-Type: application/pdf` with `Content-Disposition: attachment`.
- **Dynamic theme tokens:** when `config('site.themes.dynamic')` is ON and the active theme is neither
  `technical` nor `matrix`, `layouts/app.blade.php` emits one `<style nonce="…">:root{ --x: …; }</style>`
  built from the theme's `tokens` JSON. `technical`/`matrix` never emit this block — they keep their
  `app.css` `[data-theme]` blocks. The nonce is the same `Vite::cspNonce()` `SecurityHeaders` already
  puts in `style-src`.
- **Nav menu:** `<x-nav-menu>` is a keyboard-navigable menubar — `role="menubar"` / `menu` /
  `menuitem`, arrow-key movement, `Esc` closes an open submenu and returns focus to its trigger,
  focus is trapped within an open submenu. Per-theme look is entirely CSS custom properties
  (`--menu-bg`, `--menu-border`, `--menu-shadow`, `--menu-highlight`) so `technical` reads as a
  chrome menu and `matrix` as a terminal menu with no second component.
- **YouTube facade:** `<x-youtube-embed id="…">` renders a thumbnail (`https://i.ytimg.com/vi/{id}/hqdefault.jpg`)
  + a play button; a small nonce'd Alpine handler swaps in
  `<iframe src="https://www.youtube-nocookie.com/embed/{id}?autoplay=1">` on click. Initial HTML
  contains **no iframe**. Only reachable from Life posts (a `[youtube:ID]` shortcode expanded on
  render, matching how the repo renders RichEditor content).

### Loading, empty, error states

- `/life` with zero published life articles under a permitted theme → designed empty state (the
  seeder guarantees one row, the template still handles zero).
- `/tools` with zero published tools → designed empty state.
- `/tools/{slug}` when GitHub is unreachable → the detail page renders with the last stored
  `gh_*` column values and a muted "stats last updated {gh_fetched_at}" line; never a 5xx, never a
  blank stats block.
- `/endorsements` with zero approved testimonials → the form still renders under a "Be the first to
  endorse" heading.
- Terminal widget: an unknown command prints `command not found: <x>` in the popup; `whoami` with no
  `.mmdb` prints the IP + UA lines and `location: unavailable` for the geo lines; GPS declined prints
  `gps: permission denied` — never a silent omission.

**Inherits Phase 1 §7 verbatim** — the same palette, type scale, spacing, radius, motion rules, and

### New CSS custom properties (added to BOTH the `:root`/`@media` block and the `[data-theme="matrix"]` block, and to the `themes.tokens` documented key list)

| Token | Technical (light / dark) | Matrix | Used by |
|---|---|---|---|
| `--menu-bg` | `#FFFFFF` / `#111113` | `#000000` | `<x-nav-menu>` dropdown surface |
| `--menu-border` | `#E4E4E7` / `#27272A` | `#1F1F1F` | menu outline |
| `--menu-shadow` | `0 4px 12px rgb(0 0 0 / 0.10)` / same | `0 0 8px rgb(0 255 65 / 0.20)` | menu elevation (Matrix uses the accent glow, never on body containers) |
| `--menu-highlight` | `#E8ECF0` / `#1C1C1F` | `#0C130E` | hovered/focused `menuitem` background |

**Contrast:** `--terminal-fg` on `--terminal-bg` is ≥15:1 in both themes. `--menu-highlight` against
`--menu-bg` is a ≥3:1 UI-boundary contrast in all three palettes. The Matrix `--terminal-accent`
(`#00FF41`) is used only for the prompt glyph and cursor, never for command output text — same rule
as Phase 1's body-text ban.

### `themes.tokens` JSON schema

A flat object of `"--custom-property-name": "value"`. The admin KeyValue field in `ThemeResource`
accepts any `--*` key; the render layer only injects keys that start with `--`. The documented,
UI-hinted set an event theme is expected to override: `--color-background`, `--color-foreground`,
`--color-primary`, `--color-accent`, `--color-accent-text`, `--color-border`, `--color-ring`,
`--menu-bg`, `--menu-border`, `--menu-highlight`, `--terminal-bg`, `--terminal-fg`,
`--terminal-accent`. Seed rows `technical`/`matrix` carry `{}` — they render from `app.css`, never
from injected tokens.

### Motion / a11y

All new interactive surfaces respect `prefers-reduced-motion: reduce` (the nav dropdown appears with
no transition; the YouTube facade swap is instant). Focus rings use `--color-ring` and are never
removed, including on the terminal input and every `menuitem`.

## 9. BUILD ORDER

**48 steps, 6 epics** (8 / 8 / 9 / 9 / 9 / 5). The split follows the locked Phase-2 backlog's own
feature grouping, not an even division — Epic 01 is the staging + flag foundation everything else
needs; Epics 02–06 map one-to-one onto the backlog's reach / theming / content / platform /
testimonials clusters. This exceeds the template's default 10–18 range for the same reason Phase 1's
27-step blueprint did: the scope is a fixed, owner-locked backlog of 15 features, and each step is
still a one-sitting unit (≤5 files, ≤6 acceptance criteria). Do not merge steps to shrink the count.

### The release sub-flow — every step, without exception

Each step's four fields (`Do` / `Done when` / `Verify` / `Checkpoint`) cover implementation and the
**local** gate only. After a step's `Checkpoint`, the change goes through this flow before it is
"shipped", and the flow is **not** encoded as a step's `Verify` because two of its gates wait on a
human or on real infrastructure:

1. Open a PR from `task/<id>-<slug>` → `main`.
2. CI runs; the `ci` check must be green.
3. Merge to `main`.
4. `bash infra/deploy-staging.sh` → the change is live on `https://staging.miautrix.tech`.
5. **SPONSOR REVIEW & APPROVAL on staging** — the owner reviews the change against the epic's
   acceptance criteria and writes `review/<id>.md` with verdict `APROBADO` (or `CAMBIOS`). *This is
   an un-scriptable human gate. It is a release-checklist item (§20.1), never a step's "Done when".*
6. `bash infra/deploy.sh` — production promote. Only after `APROBADO`.
7. Live verify on production: the step's key `curl`/route checks, run against the production URL.

Steps may be batched into one review where the epic notes it (Risk #1 mitigation) — but each step is
still its own PR, its own commit, its own checkpoint tag.

### Checkpoint tags

Phase 1 used `step-01`…`step-27`. **Phase 2 tags are `p2-step-01`…`p2-step-48`** (`p2-step-NN-{slug}`)
to avoid colliding with Phase 1's `step-*` namespace. §20.1's final count greps `git tag -l 'p2-step-*'`
and expects **48**.

### One step, one unit

One §9 step = one `tasks.json` task = one task block in an epic file. 48 steps → 48 tasks → 48 task
blocks across 6 epic files. Epics group these steps; they do not subdivide them.

### 9.1 Parity and cutover

**Required** — item 9 (www ↔ apex canonicalisation) is a routing migration: the same URLs are about
to be served from a different host arrangement, and the failure mode is "themes work on only one host
at a time, and it flips day to day" — a real, reported production bug. A greenfield build has no such
concern; this one does.

#### Parity set

| # | Behaviour held constant | How parity is proved | Tolerance |
|---|---|---|---|
| 1 | Same rendered HTML on `www.miautrix.tech` and `miautrix.tech` for every route in Phase 1 §6 + every Phase-2 public route | `infra/host-parity-check.sh` — `curl -s` both hosts for each path, strip the per-request CSP nonce and CSRF token, `diff` the rest | exact match after nonce/token strip |
| 2 | Same resolved theme on both hosts for the same `miautrix_theme` cookie | the same script re-runs each path with `Cookie: miautrix_theme=matrix` and asserts `data-theme="matrix"` on both | exact match |
| 3 | Page-cache never serves one host's HTML for the other | `tests/Feature/Phase2/CacheKeyHostSegmentTest.php` (step 22) — the cache key differs by the host segment; a `www` request never reads an apex entry | exact match |
| 4 | `<link rel="canonical">` points at `canonical_host` on **both** hosts | step 23's test asserts the canonical URL host equals `config('site.canonical_host')` regardless of the request host | exact match |

**Shadow period:** both hosts stay reachable and behind the same origin for the full Phase-2 build.
`infra/host-parity-check.sh` runs after every Epic 03 staging deploy. Parity = zero diffs across all
paths on three consecutive runs over at least 48 hours. Any non-zero diff blocks the Cloudflare 301
rule from being applied.

#### Cutover

| Phase | What changes | Who is affected | Reversible by | Verify |
|---|---|---|---|---|
| Coexistence | Both hosts serve identical content; cookie domain is `.miautrix.tech`; cache key carries the host segment | nobody | already the state after step 23 | `bash infra/host-parity-check.sh` — 0 diffs |
| Canonical link | `<link rel="canonical">` on both hosts points at `canonical_host` | crawlers only | revert step 23's Blade change | step 23's test |
| 301 rule | A Cloudflare Redirect Rule 301s the non-canonical host to `canonical_host` (rule text in `infra/provision-staging.md`; the owner applies it in the Cloudflare dashboard) | every visitor on the non-canonical host | **delete the Cloudflare rule** — takes effect in seconds, no deploy | `curl -sI https://<non-canonical>/` → `301` with `Location:` on `canonical_host` |
| Decommission | Nothing in-app to remove — coexistence introduced no temporary shim (only the permanent cookie-domain, cache-key host segment, and canonical link). The Cloudflare 301 rule is permanent once parity holds. | — | — | — |

**Kill switch:** delete the Cloudflare Redirect Rule in the dashboard. Traffic returns to
"both hosts serve directly" in seconds — no deploy, no code change. The cookie-domain and
host-in-cache-key changes are safe to leave in place (they are correct either way).

#### Abort criteria

- [ ] WHEN `infra/host-parity-check.sh` reports any diff on any path THE SYSTEM SHALL NOT apply the 301 rule (and SHALL delete it if already applied).
- [ ] WHEN either host returns a 5xx rate above the pre-cutover baseline for 5 minutes THE SYSTEM SHALL delete the 301 rule and hold.
- [ ] WHEN the "wrong theme on one host" symptom recurs (a `data-theme` mismatch between hosts for the same cookie, observable in `infra/host-parity-check.sh`) THE SYSTEM SHALL delete the 301 rule and hold.

#### Data migration

NOT APPLICABLE — no data moves. The canonicalisation is a routing/redirect change plus a cookie-domain
and cache-key change. No store is repointed.

#### Decommission

There is **nothing in-app to decommission**. The canonicalisation introduces no temporary host-alias
shim — coexistence is the three permanent, correct-either-way changes (cookie domain `.miautrix.tech`,
the host segment in the cache key, the canonical link), all of which stay. The Cloudflare 301 rule
itself is permanent once parity holds; its removal is only ever the rollback / kill-switch action.
Both DNS records stay (one now 301s), and no credential or vendor account is retired.

### Bootstrap

```bash
# order matters: repo already exists -> apply workspace agent config (guarded) -> install -> build -> key -> migrate
# The repo is an existing git checkout with full history and a working tree — nothing is scaffolded.

# 1. Version control already initialised (this is an existing repo). Idempotent guard only:
git rev-parse --git-dir >/dev/null 2>&1 || git init -b main

# 2. Apply the Phase-2 agent workspace into the project root, non-clobbering. rsync -a
#    --ignore-existing skips any file already present and exits 0 whether it copies or skips
#    (unlike `cp -Rn`, which exits 1 on BSD/macOS when it skips — that would abort this block
#    under `set -e` on a re-run). NEVER overwritten once present: CLAUDE.md and AGENTS.md are
#    MERGE targets (see workspace/CLAUDE.md's header) — the copy lands them only if absent, and
#    on a repo that already has them (it does) this line changes nothing. composer.json /
#    package.json / composer.lock / package-lock.json are not under workspace/ at all.
rsync -a --ignore-existing blueprints/phase-2/workspace/. ./

# 3. Install (idempotent). npm run build BEFORE any pest run — several generated auth/settings
#    views render @vite() and throw ViteManifestNotFoundException with no public/build/manifest.json.
composer install --no-interaction
npm ci
npm run build

# 4. App key ONLY if absent. `key:generate --force` writes UNCONDITIONALLY (it just skips the
#    prompt), so it must never run on a checkout that already has a real APP_KEY — rotating a
#    live key breaks decryption of every `encrypted`-cast column (the E5-T1 SMTP password is
#    exactly that) and invalidates sessions/signed URLs. Guard on APP_KEY being blank:
php -r "file_exists('.env') || copy('.env.example', '.env');"
grep -q '^APP_KEY=$' .env && php artisan key:generate --force || true

# 5. Local Postgres only if using the docker fallback (the repo's phpunit.xml points at a
#    network Postgres by default; this is the offline path):
#    docker compose up -d && sleep 2 && docker compose exec -T postgres pg_isready -U miautrix

# 6. Migrate (idempotent — Laravel's migration table makes a re-run a no-op). Seed once.
#    `db:seed` REQUIRES ADMIN_SEED_EMAIL and ADMIN_SEED_PASSWORD in the environment (§10 env
#    table) — the repo's DatabaseSeeder aborts with RuntimeException otherwise. On the dev /
#    staging / prod nodes both are pre-set. In a bare scratch checkout export them first:
#      export ADMIN_SEED_EMAIL=admin@example.test ADMIN_SEED_PASSWORD='ScratchOnly!234'
#    Skip step 6's `db:seed` entirely if you only need schema (migrate) — E3-T1's own gate
#    seeds the theme rows through a `pest` test that runs under phpunit.xml's forced env.
php artisan migrate
[ -n "$ADMIN_SEED_EMAIL" ] && [ -n "$ADMIN_SEED_PASSWORD" ] && php artisan db:seed || echo "db:seed skipped — ADMIN_SEED_* not set (schema is applied; E3-T1's pest gate seeds themes)"
```

**Every command here is safe to run twice**, and re-running the whole block exits 0 (see §20.1's
Bootstrap re-run gate). The `git init` guard is a no-op in an existing repo, `rsync
--ignore-existing` skips and exits 0, `composer install`/`npm ci` are idempotent, the `key:generate`
line only fires when `APP_KEY` is literally blank and is a `|| true` no-op otherwise (it never
rotates an existing key), `migrate` is a documented no-op on an already-migrated database, and the
guarded `db:seed` either `updateOrCreate`s on a natural key (no duplicates) or prints its skip line
and exits 0 when `ADMIN_SEED_*` are unset. This block is executed verbatim — twice, back to back —
in a scratch checkout before this blueprint ships; a failure comes back as a finding with the real
error.

### The Phase-2 release pipeline

```
implement on task/<id>-<slug>
  -> local gate: ./vendor/bin/pint --test && ./vendor/bin/phpstan analyse && npm run build && ./vendor/bin/pest
  -> PR to main
  -> CI: the `ci` check (unchanged workflow) must be green
  -> merge to main
  -> bash infra/deploy-staging.sh        # NEW — deploys main to staging.miautrix.tech
  -> SPONSOR REVIEW & APPROVAL on staging  # NEW — human gate; review/<id>.md = APROBADO
  -> bash infra/deploy.sh                # UNCHANGED — production promote, only after APROBADO
  -> live verify on https://miautrix.tech
```

`infra/deploy-staging.sh` is a parameter-swapped copy of `infra/deploy.sh`: same local gate first,
same GitHub-pull-on-server, `migrate --force` (expand-only), atomic symlink cutover, `cache:clear`,
supervisor + fpm reload — but reads `STAGING_*` env vars, targets the staging host, sets
`APP_ENV=staging`, and points at the staging database. It **never** contains `migrate:fresh` or
`db:wipe` (re-asserted by the same grep guard `deploy.sh` uses). `infra/deploy.sh` itself is not
edited by Phase 2.

### CI/CD

The `ci` workflow is unchanged except step 7 adds `staging` to `on.push.branches` so the staging
branch runs the same gate. The job `name: ci` and every step stay exactly as they are — branch
protection's dependency on the literal check name `ci` is preserved.

### Release and rollback

- **Per-task rollback:** revert the task's PR + `php artisan migrate:rollback` (every Phase-2
  migration has a real `down()`), then redeploy. Because migrations are expand-only, a code-only
  revert (checkout the previous release tag, re-run the non-migration deploy steps) needs no
  down-migration in the same deploy.
- **Feature rollback with no redeploy:** set the relevant flag to `false` in the environment —
  `SITE_THEMES_DYNAMIC`, `SITE_ANALYTICS_RECORD_PAGE_VIEWS`, `SITE_CSP_YOUTUBE_ON_LIFE`. Each

  path, `RecordPageView` early-returns before any write, the `/life` CSP addition is not applied.
- **Canonicalisation rollback:** delete the Cloudflare 301 Redirect Rule (§9.1 kill switch) — seconds,
  no deploy.

### Domain, DNS, TLS

`staging.miautrix.tech` — a new `A`/`CNAME` record proxied through Cloudflare (orange-cloud), its
Nginx vhost carrying HTTP Basic auth and serving `APP_ENV=staging`. The apex/www canonicalisation is
a Cloudflare Redirect Rule (rule text in `infra/provision-staging.md`), applied by the owner only
after §9.1 parity holds. Origin TLS unchanged (Cloudflare Origin CA on Nginx).

### Critical flows to cover

1. Publish a `channel='life'` article → it appears on `/life` under Matrix, 404s under Console, and

2. A visitor clicks a share link → `/s/x/article/{id}` writes one `share_clicks` row and 302s to

3. A visitor downloads a tool → `/tools/{slug}/download` writes one `tool_downloads` row (geo null
   without the `.mmdb`) and streams the file; the analytics dashboard total goes up by one.
4. The owner saves SMTP settings in Filament and clicks "Send test email" → `config('mail.*')`
   reflects the saved values and a `TestMail` is dispatched (`Mail::fake`).
5. A visitor submits an endorsement → a `pending` row, invisible publicly; the owner approves it →
   it renders on `/endorsements` with the linked contact; `/endorsements` cache is busted.

### Test data

`RefreshDatabase` per class against the real PostgreSQL the repo's `phpunit.xml` points at (network
`miautrix_test`, or the docker `postgres:18.6` fallback). Factories for every new entity. GitHub is
`Http::fake()`d in `RepoStatsTest` and `ToolsPublicAdminTest`. Mail is `Mail::fake()`d in
`MailSettingsTest` and `TestimonialFormTest`. **No test requires the GeoLite2 `.mmdb`** — `GeoLocator`
returns null for every field when the file is absent, and every geo assertion is written against that

  `curl -I` in §20.1's launch checklist.

- Real MaxMind lookups — `GeoLocator`'s null path is unit-tested; the populated path is a manual
  smoke on an environment that has the `.mmdb`.
- Visual rendering of the new themes' JSON tokens — structural tests assert the `<style nonce>` block
  is emitted with the right custom properties; pixel correctness is the sponsor's staging review.

### 20.3 Decision log

| # | Decision | Rejected alternative | Why | Would reverse if |
|---|---|---|---|---|
| 1 | Special-event themes are `themes` table rows with a JSON `tokens` map injected as a nonce'd `<style>` at render | A new `[data-theme="…"]` block in `app.css` per event | Data-driven means zero deploys to add/retire a seasonal theme, and the switcher can filter by date window; app.css stays two blocks | An event theme needs CSS beyond custom-property values (keyframes, selectors) — then it needs a real stylesheet, not tokens |
| 2 | `technical`/`matrix` seeded as rows with `tokens={}` and kept rendering from `app.css` | Migrate their tokens into the `themes.tokens` JSON too | Keeps the two base themes byte-identical to Phase 1 — the flag-ON path is proven not to change them because they render from the same CSS they always did | A future refactor unifies all theme rendering through injected tokens and drops the app.css blocks |
| 3 | `barryvdh/laravel-dompdf` for PDF | Browsershot/Chromium; a hosted PDF API | Pure PHP, nothing new to run or supervise on the single LXC; the portfolio exhibits a minimal stack | A project's print view genuinely needs a real browser engine (complex CSS grid, web fonts, SVG) that dompdf cannot render |
| 4 | `geoip2/geoip2` + a local `.mmdb`, null-safe when absent | A hosted IP-geo API | No per-request third-party call (the "no tracker" rule), no vendor uptime dependency on a download path; the build never blocks on the file | MaxMind stops offering GeoLite2 for free, or the `.mmdb` becomes impractical to keep updated per environment |
| 5 | Sponsor-approval gate as a release-checklist item, not a step "Done when" | Encode it as a task the builder waits on | A human reviewing a staging URL cannot be a script-decidable gate; making it one would either stall the autonomous build forever or let it self-certify | Never — this is the correct shape for a human gate |
| 6 | Phase-2 checkpoint tags namespaced `p2-step-*` | Continue `step-28`…`step-75` from Phase 1 | Keeps Phase 1's `step-*` count (`27`) intact and makes "which phase built this" legible from the tag; §20.1 counts `p2-step-*` independently | Never — the namespaces are cheap and unambiguous |
| 7 | `RecordPageView` appended to the global middleware stack, flag-gated | A route-group middleware on `cache.public` only | Analytics needs `/admin`-excluded but otherwise every public GET, including routes outside `cache.public` (`/contact`, downloads); the global stack with an early-return is simpler than maintaining a second route list | The early-return fast path measurably regresses latency even with the flag on — then move it behind the cache and accept missing the uncached routes |
| 8 | Page-cache key gains a **leading** host segment (`public-page:{host}:{theme}:{path}`) | Rebuild the key entirely, or hash the whole request | Additive — every existing invalidation call still works with one extra argument; a leading segment is trivially greppable and never collides with the existing `{theme}:{path}` tail | The host set grows beyond apex/www/staging and the key needs a registrable-domain normalisation step |
