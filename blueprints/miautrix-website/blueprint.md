## 1. Project Overview & Non-Goals

### Vision

miautrix-website is a self-hosted portfolio platform for one enterprise IT professional. It presents an
infrastructure-and-project-management career — infrastructure projects, software projects,
certifications, experience, skills, technologies and downloadable resumes — through a fast, static-feeling
public site, and it is administered entirely through a secure Filament CMS. The owner never edits code to
publish: every entity, every image, every resume version and every SEO field is a form in the admin panel.

The application is **itself** the exhibit. A recruiter who reads the public site sees the career; a hiring
engineer who opens the repository sees the architecture, the CI pipeline, the test suite, the security
posture and the deployment model. That means code quality, the pipeline and the operational story are part
of the deliverable and not incidental to it — which is why deployment is Epic 01 rather than the last epic,
and why the security decisions in §14 are stricter than a one-user site would otherwise justify.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|
| The owner (sole administrator) | Publish and edit career content, upload media and resume versions, read the audit log | Weekly |
| Recruiter | Skim experience, certifications and a resume PDF in under two minutes | Once per candidate evaluation |
| Hiring engineer / technical reviewer | Read project detail pages and the repository itself to judge engineering quality | Once, deeply |
| Search and answer engines | Crawl and cite structured, per-entity metadata | Continuously |

### Goals — v1 scope

1. The public site renders every published entity — profile, experience, education, companies,
   certifications, skills, technologies, projects, software projects, resumes, social profiles — with
   per-entity SEO metadata, JSON-LD, a generated sitemap and a dark mode.
2. A single administrator manages 100% of that content through a Filament admin portal with mandatory
   TOTP MFA, role-backed policies and an append-only audit log, without touching code.
3. The platform runs on infrastructure the owner controls — a Debian 13 LXC behind Cloudflare — with a
   zero-downtime deploy script, a supervised queue worker, Redis caching, nightly backups and an
   *executed* restore drill.
4. Every change reaches production through a protected `main`, a green GitHub Actions pipeline
   (Pint, Larastan, Pest, Vite build) and a reviewed pull request.
5. The build is resumable and auditable: 24 steps, each with machine-checkable acceptance criteria, a
   runnable verify command and a git checkpoint tag.

### Non-Goals — explicitly out of scope for v1

| Not building | Why not now | Revisit when |
|---|---|---|
| **LinkedIn import** | LinkedIn's API needs partner approval that is not obtainable on demand; building against it is a coin flip on someone else's review queue | v2, and only as an **export-file** (`.zip`/`.csv`) importer behind the same admin review queue |
| **GitHub *content* import** (repo → portfolio project) | Deferred to v1.1 so v1 ships. **This is NOT GitHub-as-development-platform** — the remote, pull requests and Actions are in v1 from step 2 and are never in question. The two are different things and must never be conflated | v1.1, once the `PortfolioIntegration` seam created in step 9 has one real consumer |
| Multi-theme switching | One theme plus dark mode covers the audience. CSS custom properties make theme #2 a config change, not a refactor | A second brand or a client asks for one |
| Blog / technical articles | A content treadmill the owner has not committed to. Every published article that goes stale costs credibility | The owner writes three drafts before asking for the feature |
| Public JSON API (`/api/v1/*`) | No consumer exists. An unused public API is pure attack surface plus a versioning obligation | A real third-party integration is named |
| Multi-language | The audience is one enterprise IT market. i18n doubles every content entity's editing cost | The owner targets a second-language market |
| Dynamic PDF resume generation | Uploaded, versioned PDFs are better-designed than anything generated, and the download counter gives the same analytics | Resume variants exceed what manual curation can keep in sync |
| Complex RBAC and multiple administrators | There is one administrator. The `roles`/`permissions` tables **are** installed and one `super_admin` is seeded, so expansion is additive rather than a migration | A second person needs write access |
| Global full-text search | Content volume is a few hundred rows. Browsing and filtering beat search at that size | The catalogue passes ~500 published entities |
| S3 / object storage | Local disk on the LXC with nightly off-host backup meets the durability requirement. The `Storage` facade makes the driver swap a config change | Media exceeds the LXC disk budget or a CDN origin is needed |
| Analytics vendor integration | An `AnalyticsProviderInterface` with a null implementation ships in step 9. No vendor means no cookie banner, no consent flow and no third-party script in the CSP | The owner wants real traffic data and accepts the privacy and CSP cost |

**The builder must not implement anything in this table**, even if it looks like a small addition while
working on an adjacent step. If a step appears to require a non-goal, that is a blueprint defect — stop and
report it rather than expanding scope.

### Success metrics

| Metric | Target | How measured |
|---|---|---|
| Public page performance | Lighthouse performance ≥95 and SEO ≥95 on the home page and one project detail page, throttled mobile profile | `bash scripts/lighthouse-gate.sh` (step 23) |
| SEO surface completeness | Zero missing titles, zero duplicate meta descriptions, zero canonical mismatches across every public route | `php artisan seo:audit` (step 22) |
| Content self-service | Zero code changes required to publish any entity in §4 | Every entity in §4 has a Filament resource (steps 14–17) |
| Recoverability | A restore drill restores last night's dump into a scratch database and every table's row count matches | `bash infra/backup/restore-drill.sh` (step 24) |
| Release safety | 100% of production releases come from a green `ci` run on protected `main` | Branch protection read back by `scripts/github-assert-protection.sh` (step 2) |

## 2. Tech Stack

**Runtime track: rails-laravel, sub-track B (Laravel).** This table names *choices*, not versions. Every
version pin lives in §11 and nowhere else.

The track's default for a `marketing-site` shape is TypeScript/Astro. It was **deliberately overridden**:
the content here is database-driven and admin-authored, not markdown files in a repository, and the admin
CMS is roughly 70% of the build. `knowledge/shapes/internal-tool.md` says so directly — "if the stack
already ships an admin, a bespoke build must be justified by a requirement the built-in admin genuinely
cannot meet". Filament generates the entire back office from Eloquent models; nothing in the JavaScript
ecosystem is close on effort-to-result for 18 CRUD entities.

| Layer | Choice | Why this, over what |
|---|---|---|
| Language / runtime | PHP | Over TypeScript: the whole product is forms over a database plus server-rendered pages. One process model, one deployable, no edge/runtime split |
| Framework | Laravel | Over Symfony: the batteries — queues, mail, cache, scheduler, storage, auth scaffolding — are the parts we would otherwise assemble, and Filament exists only here |
| Interactivity | Livewire + Alpine | Over Inertia+React: the public site is content, the admin is Filament (which *is* Livewire). Adding a SPA bridge would mean two rendering models for zero interaction we actually have |
| Styling | Tailwind CSS v4 via `@tailwindcss/vite` | Over hand-written CSS: the design system is token-driven and the v4 CSS-first `@theme` layer expresses the palette in §7 directly. Over CSS-in-JS: no client runtime, no cascade fight |
| Component layer | Blade components (public) + Filament (admin) | Over a shared component library: the two surfaces have opposite requirements — public is bespoke and marketing-grade, admin is generated and dense |
| Database | PostgreSQL 18 | Over MySQL: partial indexes, `jsonb` for the audit log's before/after payloads, and stricter constraint behaviour. Over SQLite: the content is the irreplaceable asset and deserves real backup tooling |
| ORM / data access | Eloquent, directly | Over a repository layer: the track is explicit that a repository over Eloquent buys nothing. Real domain logic goes in `app/Actions/` single-public-method classes; `app/Services/` is only for external-integration clients |
| Auth | Laravel Fortify (headless) + spatie/laravel-permission | Over a hosted identity provider: one user, self-hosted, no vendor. Fortify gives TOTP two-factor and recovery codes without the Breeze/Jetstream UI we would throw away |
| Background work | Redis queue + Horizon, supervised by supervisor | Over the database driver: Horizon's dashboard and failed-job visibility are worth the Redis dependency we already have for cache and sessions |
| Payments | NOT APPLICABLE | Nothing is sold. No payment surface exists in v1 or in the non-goals |
| File storage | Local disk on the LXC, `media_private` outside the web root, served through a controller | Over S3: durability is met by nightly off-host backups. The `Storage` facade makes the swap a config change (§1 non-goals) |
| Email / notifications | Laravel Mail, `log` driver locally, SMTP in production | Over a transactional-email vendor: one contact form and no marketing mail. A vendor is an account, a key and a deliverability surface for a single message type |
| Hosting | Self-hosted Debian 13 LXC behind Nginx and Cloudflare | Over Laravel Cloud/Forge: "self-hosted" is a stated product requirement and part of what the portfolio demonstrates |
| Package manager | Composer (PHP) + npm (JS), per the runtime track | Track default. `composer.lock` and `package-lock.json` are committed and CI installs from them |

### Compatibility check

**Checked against `knowledge/stack-compatibility.md` — none of the rows below apply at the pins in §11.**

The one row that could have applied is *"Admin/UI framework + a different major of the component runtime
it is built on"*. It was checked explicitly: `filament/support@5.7.8` requires `livewire/livewire: ^4.1`
and `illuminate/contracts: ^11.28|^12.0|^13.0`; the pinned Livewire is 4.4.3 and the pinned framework is
13.30.1. **There is no Filament 5 / Livewire 3 conflict at these pins.** The standing obligation from that
row survives: Filament and Livewire are upgraded **together**, on the 5.x/4.x lines, never one alone.

Two other rows were considered and do not apply. *"Linter/formatter that parses CSS itself + CSS-first
styling engine"*: Pint formats PHP only and has no CSS parser, so Tailwind v4's `@theme`/`@source` at-rules
are never parsed by the linter. *"Long-lived process design + request-scoped host"*: the host is a
long-lived LXC, which is exactly what the queue worker and scheduler need.

**Hard constraints discovered during version verification, stated as facts of this project:**

- **PHP 8.4 is a hard floor, driven by the test runner and not by the framework.** `pestphp/pest@5.1.3`
  requires `php: ^8.4`; `laravel/framework@13.30.1` only requires `^8.3`. The LXC must install PHP 8.4 or
  higher (8.5.10 is current stable). A machine on 8.3 will install Laravel fine and fail to install Pest,
  which reads as a broken dependency tree rather than as a PHP version problem.
- **Flux UI is not used, deliberately.** `livewire/flux-pro` returns HTTP 404 on Packagist — it is a paid,
  private Composer repository — and the free `livewire/flux` tier (v2.18.0) is proprietary-licensed.
  Filament owns the admin surface and the public site is bespoke Blade + Tailwind, so neither tier is
  needed. Recorded again in §11 *Deliberately not used*.

**Track gotchas carried forward into this build, each with the step that owns it:**

| Gotcha | Owning step |
|---|---|
| Livewire re-renders on every action — `wire:model.blur` by default, `#[Computed]` for derived data | 13, 19, 21 |
| Telescope in production fills the database — gate it to `local` **and** `TELESCOPE_ENABLED=true` | 13 |
| Every model needs an explicit `$fillable`; `$guarded = []` is a loaded gun | 6–9 |
| `migrate:fresh` never appears in a deploy script | 24 |
| Queue `--tries` set explicitly, with a `failed_jobs` alert | 24 |
| A Laravel app with no supervised worker silently accumulates jobs | 24 |
| Validation in FormRequests, authorization in Policies — never inline in a controller | 10, 11, 21 |
| No repository layer over Eloquent | 6–9 |

**Boundary rules**

- `app/Http/Controllers/**` finds, authorizes, delegates and responds. It never validates inline and never
  contains a role check — validation is a FormRequest, authorization is a Policy.
- `app/Actions/**` may use models and other Actions. It may never reference the HTTP request or a view.
- `resources/views/**` never queries the database. View data arrives from the controller or a `#[Computed]`.
- `app/Models/**` holds casts, relations, scopes and `$fillable`. No HTTP, no view, no queue dispatch.
- Nothing outside `app/Http/Controllers/MediaController.php` reads from the `media_private` disk.
- `infra/**` is production-only. Nothing under `app/` or `resources/` may reference a path in it.

**Resolution convention.** This project's only import convention is **PSR-4 through Composer's
autoloader** — `App\` → `app/`, `Database\{Factories,Seeders}\` → `database/`, `Tests\` → `tests/`, all
declared in the scaffolded `composer.json`. There are no path aliases, no barrel files and no extensionless
specifiers. Blade resolves views by dotted name from `resources/views/`; Vite resolves only
`resources/css/app.css` and `resources/js/app.js`. That convention is reconciled against every loader in
**§19.6's resolution convention matrix**, which is the only place the per-context settings are stated.

**Every output path drawn above is a value some emitted config also states.** The literals — `public/build`,
`tests/`, `blueprints/`, `miautrix_test`, port 5432, port 6379 — are reconciled in §19.6's
*Cross-artifact value reconciliation* table. This tree is documentation: drawing a file here creates
nothing. Every file above has exactly one origin — a §9 step's **Do** list (and that task's `files` array),
or emission under `workspace/` per §19.6.

## 4. Data Model

Every content entity is *publishable*: it carries `slug` (unique, indexed), `published` (boolean, indexed,
default `false`), `featured` (boolean, default `false`), `sort_order` (integer, default 0), the SEO block
(`seo_title`, `meta_description`, `canonical_url`, `og_title`, `og_description`, `og_image_id`),
`created_at`/`updated_at`, and `deleted_at` (soft delete). That shared block lives in the
`app/Models/Concerns/Publishable.php` trait and in a migration macro; it is not restated per entity below.

validation error. `audit_logs` are never deleted by the application; retention is an operator decision
executed by a documented SQL statement in `docs/runbook.md`, never by application code.

### Schema

The schema is expressed as Laravel migrations, not as hand-written SQL. **Migration filenames are chosen by
`php artisan make:migration` and are never written into this blueprint** — refer to "the migration that
`php artisan make:migration create_experiences_table` emitted". The publishable block is applied by a
shared macro so it cannot drift:

```php
// database/migrations/... (the migration `php artisan make:migration add_publishable_macro` emits)
// Registered once in a service provider; every content migration then calls $table->publishable().
Blueprint::macro('publishable', function () {
    /** @var \Illuminate\Database\Schema\Blueprint $this */
    $this->string('slug', 180)->unique();
    $this->boolean('published')->default(false)->index();
    $this->boolean('featured')->default(false);
    $this->integer('sort_order')->default(0);
    $this->string('seo_title', 180)->nullable();
    $this->string('meta_description', 320)->nullable();
    $this->string('canonical_url', 255)->nullable();
    $this->string('og_title', 180)->nullable();
    $this->string('og_description', 320)->nullable();
    $this->foreignId('og_image_id')->nullable()->constrained('media')->nullOnDelete();
    $this->timestamps();
    $this->softDeletes();
    $this->index(['published', 'sort_order']);
});
```

Because `og_image_id` references `media`, every content migration that calls `publishable()` runs **after**
medialibrary's own migration. Step 6 therefore publishes medialibrary's migration first (the package is
installed in §10 Bootstrap) and step 16 only adds the hardening, the `project_media` pivot and the serving
controller. This ordering is a stated fact of the build, not an accident of numbering.

### Migrations

- Tool: Laravel migrations. Create with `php artisan make:migration`, run with `php artisan migrate --force`.
- **Never edit a migration that has run** on any environment. Add a new one.
- **Expand-then-contract in production.** A column is added and backfilled in release N; the code that
  stops writing the old column ships in release N; the drop ships in release N+1. `infra/deploy.sh` runs
  `migrate --force` and contains no destructive statement.
- `php artisan migrate:fresh` is a local reset only. It is in `.claude/settings.json`'s deny list and
  appears in no script, no CI job and no deploy path.

### Seed data

A fresh local database gets, from `php artisan db:seed --force`:

- `database/seeders/RoleSeeder.php` — the `super_admin` role and the permission set (step 11).
- `database/seeders/AdminUserSeeder.php` — one administrator, MFA **not** yet enrolled, so the enrolment
  flow is exercised on first login (step 13).
- `database/seeders/DemoContentSeeder.php` — a **realistic** portfolio: one profile, 4 companies,
  6 experiences, 2 education rows, 8 certifications, 5 skill categories with 24 skills, 20 technologies,
  3 project categories, 9 projects of which 4 have a `software_projects` extension, 3 documents with one
  current resume, and 5 social profiles (step 12). This exists because **content supply, not code, is the
  real bottleneck** (§20.2 risk 1) — the build must never block waiting for the owner to write copy.
- Seeders are idempotent: every row is `updateOrCreate` keyed on `slug`, so a second run changes nothing.

## 5. API Design

**No public JSON API in v1** (§1 non-goal 5) — every route in this section is either a Blade page, a
Livewire/Filament component, or one of the four narrow internal endpoints below. There is no
`/api/v1/*` surface, no envelope, no pagination convention and no rate-limit tier to design, because
nothing consumes one.

### Internal endpoints — full detail

| Method | Path | Description | Auth | Rate limit |
|---|---|---|---|---|
| `POST` | `/contact` | Contact form submission | public | 5/hour per IP, honeypot field `_gotcha` |
| `GET` | `/resume/{document}` | Resume/document download, increments counter | public if `published`, else `auth` | 30/hour per IP |
| `GET` | `/media/{media}` | Serves a private upload | policy-checked per referencing entity | none (authenticated surface) |
| `GET` | `/health` | Deep health check | public | none — polled by uptime monitoring |

**`POST /contact`** — request: `name` (string, 2-120), `email` (email, required), `message` (string,
10-2000), `_gotcha` (must be empty). Response: `302` back to the referring page with a flashed
`status=sent` on success, or `422` with field errors rendered inline (never a top-of-page list —
§15). Side effects: one `Mail::send` on the `log` driver locally / SMTP in production to
`CONTACT_TO_ADDRESS`; **no database row is written** — the message is not stored, only mailed, which
is the whole retention policy (§14). A non-empty `_gotcha` returns `302` with `status=sent` (so a bot
believes it worked) and sends no mail.

**`GET /resume/{document}`** — 404 if the document is unpublished and the requester is not
authenticated; otherwise streams the file from the `media_private` disk via `MediaController` with
`Content-Disposition: attachment` and atomically increments `documents.download_count` in the same
request (`increment()`, not read-modify-write, to survive concurrent downloads). Returns `410` if the
underlying `media` row was hard-deleted (which the deletion policy in §4 should have already
prevented — `410` here is a defence-in-depth assertion, not the primary control).

**`GET /media/{media}`** — every reference is policy-checked: the controller resolves which model
references the requested `media` row and asks that model's Policy `view` method, so a media file
attached only to an unpublished project is unreachable to the public. `403` on denial, `404` if no
entity references the media id at all (an orphan cannot be served by guessing its id).

**`GET /health`** — returns `200` with `{"status":"ok","database":"ok","redis":"ok","migrations":"current"}`
when the database accepts a `SELECT 1`, Redis answers `PING`, and `php artisan migrate:status` reports
no pending migration; `503` with the same shape naming whichever check failed otherwise. Never checks
an external service — only what this deployment itself depends on.

- Max content width: 1120px. Breakpoints: 375, 768, 1024, 1440 (the four widths every accessibility

200–350ms, `ease-out`, transform and opacity only — no width/height/top/left animation. Scroll reveal

renders the final state immediately — checked mechanically in step 19's `Verify`.

an engineering changelog rather than a marketing story. A new component belongs in this system only
if it uses exclusively the tokens above — a component that needs a color or radius not in this table

## 8. Authentication & Authorization

### Provider and rationale

**Laravel Fortify** (headless auth backend) + **`spatie/laravel-permission`** (roles/permissions). One
self-hosted administrator: a hosted identity provider (Clerk/Auth0) buys nothing for a single account
and adds an external dependency to a project whose point is being self-hosted. Fortify gives session
auth, password reset and TOTP two-factor without the Breeze/Jetstream UI scaffold, which this project
does not need (the only "sign-in" surface is `/admin/login`, styled to match §7, not Breeze's default
views).

### Flows

**Sign-in** → `/admin/login` (Fortify view, restyled) → credentials checked → if `two_factor_confirmed_at`
is set, redirect to `/admin/two-factor-challenge` (TOTP code) → session established → `/admin`
dashboard. **First login** (seeded admin, MFA not yet enrolled per step 12's seeder) → forced to
`/admin/two-factor-setup` before any other panel route is reachable, enforced by
`EnsureTwoFactorEnabled` — the QR code and eight recovery codes are shown exactly once, and the panel
displays a one-time banner instructing the owner to store the codes before continuing. **Password
reset** → Fortify's token-based flow, email sent via the `log`/SMTP mailer, token expires after 60
minutes. **Session expiry** → `SESSION_LIFETIME=60` minutes of inactivity, then redirect to login with
a flashed "session expired" notice. **Sign-out** → invalidates the session and regenerates the CSRF
token. **Account deletion** → **not implemented** — there is exactly one account and deleting it would
lock the owner out of their own site; this is a deliberate omission, not an oversight, and is recorded
in §20.3.

**Failure branches:** wrong password → generic "these credentials do not match" (never reveals whether
the email exists), rate-limited after 5 attempts/minute per IP+email pair, and the attempt is written
to `audit_logs` with `action=login_failed`. Wrong TOTP code → same generic message, same rate limit,
same audit row. Expired reset token → "this link has expired, request a new one."

### Route protection

| Surface | Rule | Enforced where |
|---|---|---|
| `/admin/*` | authenticated **and** `two_factor_confirmed_at` not null | `app/Http/Middleware/EnsureTwoFactorEnabled.php`, registered on the Filament panel's `middleware()` in `AdminPanelProvider` |
| `/media/{media}` | policy `view` on the model that references it | `MediaController::show`, calls `Gate::authorize` explicitly (not route-middleware, because the target model is resolved at runtime) |
| `/resume/{document}` | `published` OR authenticated | `ResumeDownloadController::show` |
| every Filament resource's create/update/delete | `super_admin` role (v1 has exactly one role, but the check is role-based from day one, per §1 non-goal 8) | the model's `Policy`, auto-discovered by Filament |

**Enforcement rule:** every check above runs server-side, per request, in a Policy or a middleware —
never a hidden button or a client-side redirect. Filament resources declare no ad-hoc `can()` closures
in the resource class itself; the Policy is the single source and the resource inherits it
automatically.

### Roles and permissions

| Role | Can | Cannot |
|---|---|---|
| `super_admin` | Full CRUD on every content entity, view audit log, manage settings, manage media | Nothing is withheld — it is the only role in v1 |

The `roles`/`permissions`/`model_has_roles` tables exist and are seeded with this one role (step 11)
specifically so a second role is additive: a future `editor` role is a seeder row and a Policy
condition, not a migration.

### Sessions

Cookie session (`SESSION_DRIVER=redis`, backed by the Redis instance already in the stack — no
separate session store). `HttpOnly` and `SameSite=Lax` always; `Secure` is `false` locally
(`SESSION_SECURE_COOKIE=false` in `.env.example`, over plain HTTP on 127.0.0.1) and `true` in
production (set in the production `.env`, never in a committed file). `SESSION_ENCRYPT=true`. CSRF:
Laravel's built-in per-session token, verified on every non-GET request via the framework's default
`VerifyCsrfToken` middleware — no custom implementation.

### Multi-tenancy / row-level isolation

**Not applicable.** There is one tenant (the owner) and one dataset; no query is ever scoped by an
organization or account boundary, and none will be added in v1 (§1 non-goal 8).

### Bootstrap

```bash
# order matters: ignore file + exceptions -> repo init -> first commit -> install -> services -> migrate -> seed

# 1. The ignore file exists before anything is added. The repo already has one committed
#    (.gitattributes only, from the initial commit) but no .gitignore yet — write it now, verbatim
#    to the one already emitted under workspace/.gitignore, BEFORE the scaffold's own first commit.
cp -n workspace/.gitignore .gitignore    # -n: no-clobber, exits 0 whether or not it already exists

# 2. Idempotent repo init (the target project root already has a repo from the initial commit --
#    this is a no-op here, kept for portability to a truly empty clone).
git rev-parse --git-dir >/dev/null 2>&1 || git init -b main

# 3. Scaffold. laravel new authors composer.json and package.json (the manifest ruling, §2/§11).
#    --livewire wires Livewire's starter kit; --pest sets Pest as the test runner.
composer create-project laravel/laravel . --no-interaction --prefer-dist
composer require --no-interaction laravel/installer:^5.32

composer require --no-interaction livewire/livewire:^4.4
composer require --no-interaction --dev pestphp/pest:^5.1 pestphp/pest-plugin-laravel:^5.1
php artisan pest:install --no-interaction

npm install --no-audit --no-fund
npm install --save-dev @tailwindcss/vite@^4.3.3 tailwindcss@^4.3.3
npm install alpinejs@^3.17

# 4. Pinned tooling from S11, edits on top of the scaffold -- named commands, after the scaffold.
composer require --no-interaction --dev laravel/pint:^1.30 larastan/larastan:^3.11 laravel/telescope:^5.23
composer require --no-interaction laravel/fortify:^1.39 laravel/sanctum:^4.3 laravel/horizon:^5.48 \
  filament/filament:^5.7 spatie/laravel-permission:^8.3 spatie/laravel-medialibrary:^11.23 \
  spatie/laravel-sitemap:^8.2 predis/predis:^3.6 laravel/boost:^2.7

# 5. Copy the emitted workspace config over the scaffold, guarded so a re-run never reverts an
#    installed dependency (the manifest is NOT among these files -- see the manifest ruling).
cp -n workspace/phpstan.neon workspace/pint.json workspace/phpunit.xml workspace/docker-compose.yml .
mkdir -p tests && cp -n workspace/tests/Pest.php workspace/tests/TestCase.php tests/
mkdir -p .github/workflows && cp -n workspace/.github/workflows/ci.yml .github/workflows/
mkdir -p .claude && rsync -a --ignore-existing workspace/.claude/. .claude/   # -Rn is not exit-0-on-skip on BSD/macOS cp; rsync --ignore-existing is

# 6. First commit -- everything on disk at this moment, with .gitignore already excluding
#    vendor/node_modules/.env, and negating .env.example back in.
cp -n workspace/.env.example .env.example
cp .env.example .env
php artisan key:generate --force
git add -A && git commit -m "chore: scaffold" --allow-empty

# 7. Local services (docker-compose.yml is now in place from step 5 above).
docker compose up -d --wait

# 8. Migrate + seed.
php artisan migrate --force
php artisan db:seed --force
```

**Re-run safety.** Every `composer require`/`npm install` line is idempotent (a satisfied constraint
is a no-op). Every `cp -n` exits 0 whether or not the target already exists (GNU/BSD both agree on
this for the non-recursive case). The recursive `.claude/` copy uses `rsync -a --ignore-existing`
instead of `cp -Rn`, because `cp -Rn` exits 1 on a skipped file under BSD/macOS `cp` — `rsync
--ignore-existing` is exit-0 on every platform regardless of what it skips. `docker
compose up -d --wait` is idempotent. `git init -b main` is guarded. `php artisan migrate --force` is
idempotent (already-run migrations are skipped). `php artisan db:seed --force` is idempotent by
design (§4, §12 — every seeder uses `updateOrCreate`).

## 12. Deployment Strategy

### Hosting

Self-hosted Debian 13 LXC on Proxmox, provisioned by the user (2 vCPU / 4GB RAM / 30GB disk — risk 6),
behind Cloudflare (proxied DNS, TLS terminated at Cloudflare's edge, `SESSION_SECURE_COOKIE=true` in
production because the origin only ever receives HTTPS from Cloudflare). Build output: `public/build/`
(Vite) alongside the standard Laravel `public/` document root, served by Nginx + PHP-FPM. Chosen over
Laravel Cloud/Forge because "self-hosted" is a stated product requirement and is itself part of the
portfolio's demonstrated engineering (§1).

### Environments

| Environment | Branch | URL | Database | Third-party mode |
|---|---|---|---|---|
| Local | any | `http://127.0.0.1:8000` | `docker-compose.yml` PostgreSQL/Redis | `MAIL_MAILER=log`, `TELESCOPE_ENABLED=true` |
| CI | `task/**`, PRs, `main`, `develop` | none (headless) | GitHub Actions service containers (Postgres 18 + Redis 8) | no third parties invoked |
| Production | `main` only | `https://$APP_DOMAIN` | Production PostgreSQL 18 on the LXC | live SMTP if configured, else `log` driver |

There is no staging/preview environment — a single-administrator, self-hosted, no-signup site has no
population to preview against; `main`'s CI gate is the promotion check.

### CI/CD

`.github/workflows/ci.yml` (emitted under `workspace/`, exercised in step 3): checkout → PHP 8.4 setup
with the exact extensions the stack needs → Node 24 setup → `composer install` → `composer audit` →
`pint --test` → `phpstan analyse` → `migrate --force` against the service containers → `pest --ci` →
`npm ci` → `npm audit --audit-level=high` → `npm run build` → asserts a build manifest exists. CI runs
**the same Pint/PHPStan/Pest/build subset** as §9's step-1 local gate, plus the two dependency-audit
checks neither local gate names explicitly (§14). It intentionally does **not** run the production
HTTPS check, the Lighthouse gate, or the backup restore drill from §20.1 — those need a real deployed
target and a real LXC, which CI's ephemeral runner is not.

### Release and rollback

`infra/deploy.sh` (final version, step 24): rsync a timestamped release, install dependencies with
`--no-dev`, run `migrate --force` (**expand-only** — a column is added and backfilled in one release;
the code that stops writing it and the `DROP COLUMN` ship in a later release, never the same one),
cache-warm (`config:cache route:cache view:cache`), atomically symlink `current`, restart the queue
worker and reload PHP-FPM/Nginx, prune to the last 5 releases. Rollback: `infra/deploy.sh`'s
`rollback.sh` companion repoints `current` at the previous release and restarts the queue — seconds,
not a redeploy — but **never reverses a migration**, which is exactly why migrations are expand-only.

### Domain, DNS, TLS

DNS: `A`/`AAAA` records at Cloudflare, proxied (orange-clouded), pointed at the LXC's public IP.
TLS: Cloudflare's edge certificate (automatic) terminates the public connection; the LXC's Nginx
listens on plain HTTP behind Cloudflare's proxy, with Cloudflare's origin IP range allow-listed in
UFW alongside the restricted SSH port (step 4). No apex/`www` redirect is needed — a single canonical
hostname is used throughout (`APP_DOMAIN`), asserted by the SEO audit (step 22) that every canonical
URL matches it exactly.

## 13. Testing Strategy

| Layer | Framework | What it covers | Where | Runs |
|---|---|---|---|---|
| Unit | Pest | Rules (`SafeUpload`), Actions, Support classes (`JsonLd`) | `tests/Unit/` | every commit (CI) |
| Feature | Pest + `RefreshDatabase` | Schema, auth/MFA, authorization, admin resources, public pages, SEO, media upload, contact form, cache invalidation — against a real PostgreSQL 18 | `tests/Feature/` | every commit (CI) |
| E2E / operational | Shell scripts (`scripts/*.sh`, `infra/backup/restore-drill.sh`) | Deploy, LXC provisioning, backup/restore, Lighthouse budget | `scripts/`, `infra/` | pre-deploy (steps 4, 5, 23, 24) and manually before any production release |

### Critical flows to cover E2E

1. **Login → MFA enrolment → admin dashboard** (steps 10, 13) — the only account on the site; a
   broken MFA flow locks the owner out entirely.
2. **Publish a project in Filament → it appears on the public site → cache invalidates → SEO surface
   updates** (steps 15, 20-23) — the entire content-authoring loop the product exists to provide.
3. **Backup → restore drill → row counts match** (step 24) — the only defense against data loss on a
   single-server deployment (risk 5).

### Test data

`tests/TestCase.php` calls `Http::preventStrayRequests()` so no test can silently reach a real
network endpoint. Feature tests use `RefreshDatabase` against the real `miautrix_test` PostgreSQL
database defined in `phpunit.xml` (never SQLite — the schema uses PostgreSQL-specific partial unique
indexes and check constraints SQLite accepts silently and differently). `docker-compose.yml`
(emitted under `workspace/`) provisions that database locally; CI provisions the equivalent as a
service container (§12). Model factories (step 12) generate fixtures per test; no test depends on
another test's data or on execution order (`phpunit.xml`'s `executionOrder="random"` enforces this).

### What is deliberately not tested

Visual regression / pixel-diff testing — the component library (step 19) is asserted structurally
(every primitive renders with no unstyled element) rather than by screenshot comparison, which is a
maintenance cost this one-administrator project does not need. Load/stress testing — v1's expected
traffic (a portfolio site, not a product with paying users) does not justify it; revisit if traffic
data after launch suggests otherwise (§16).

## 14. Security & Secrets

| Concern | Control | Implemented in |
|---|---|---|
| Secret storage | `.env` on the LXC only, never in the repo; `.env.example` carries every key blank | `.gitignore`, `config/required_env.php` |
| Secret rotation | Manual — rotate `APP_KEY`, DB password and `GITHUB_TOKEN` if ever exposed; documented procedure | `docs/runbook.md` |
| Input validation | Laravel FormRequests, one per mutating route/Livewire action | `app/Http/Requests/*` |
| Output encoding / XSS | Blade's automatic `{{ }}` escaping everywhere; `responsibilities`/`body`/`summary` markdown is rendered server-side and sanitized before storage | `app/Actions/*` (the sanitizing action), Blade templates |
| SQL injection | Eloquent/query builder parameterized queries exclusively — no raw string-built SQL anywhere | `app/Models/*` |
| AuthN / AuthZ | Fortify + mandatory TOTP MFA, spatie/permission + Policies — see §8, enforced server-side on every request | `app/Http/Middleware/EnsureTwoFactorEnabled.php`, `app/Policies/*` |
| CSRF | Laravel's built-in per-session token on every non-GET request | framework default (`VerifyCsrfToken`) |
| Rate limiting / abuse | Login 5/min per IP+email, contact form 5/hour per IP | `app/Providers/FortifyServiceProvider.php`, `RateLimiter::for('contact', ...)` |
| Webhook verification | Not applicable — no webhook receiver exists in v1 (no third-party integration is live; the `PortfolioIntegration` seam has zero implementations) | — |
| Dependency audit | `composer audit` + `npm audit` in CI, failing the build on any high/critical advisory | `.github/workflows/ci.yml` |
| Security headers | CSP (nonce, no `unsafe-inline`), HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Permissions-Policy` | `app/Http/Middleware/SecurityHeaders.php` (step 24) |
| PII handling | Contact form messages are mailed, never stored (§5); the only stored PII is the single administrator's own account | `app/Livewire/ContactForm.php` |
| Logging hygiene | `audit_logs.before`/`after` redact any field named `password`/`token`/`secret`; application logs never print a header or env value | `app/Observers/AuditLogObserver.php` |

**Hard rules**

- No secret is ever committed, printed in a log, sent to an error tracker, or embedded in a client
  bundle.
- All server-side authorization checks (Policies) run before the mutation, never after.
- There are no third-party webhooks to verify in v1 — if one is added post-v1 (e.g. a future GitHub
  import, §1 non-goal 2), it is signature-verified before its body is parsed, per this project's own
  standing rule.

**Regulated data:** none. No payments, no health data, no data belonging to minors, and the only EU/US
personal data processed is what a visitor voluntarily types into the contact form, which is mailed
and not retained (§5) — this is a deliberate design choice that sidesteps a retention-policy
obligation rather than an oversight.

## 15. Accessibility

**Target: WCAG 2.2 Level AA**, per §7's tokens and `.claude/rules/frontend.md`. Every criterion below
is a §9 "Done when" line already (steps 18–21), restated here as the audit surface.

### Baseline requirements

Semantic HTML with one `<h1>` per page (step 18, 20); full keyboard reachability with a visible
focus ring using `--color-ring` (§7); WCAG contrast already satisfied by the token table in §7 (every
pair measured ≥4.5:1); every form input has a programmatic, visible label — never placeholder-only
(step 21's contact form, `.claude/rules/frontend.md`); meaningful images carry alt text, decorative
ones `alt=""`; all motion respects `prefers-reduced-motion: reduce` (step 19); usable at 200% zoom and
320px wide with no horizontal scroll (checked at 375/768/1024/1440, step 19/20); async status changes
(the contact form's submit state) use `aria-live`.

### WCAG 2.2 additions

2.4.11 Focus Not Obscured — the sticky header (step 18) never fully covers a focused element, checked
in the layout test. 2.5.7 Dragging — the only drag-like interaction (the image gallery lightbox, step
6/21) has button-based next/previous controls, no drag-only path. 2.5.8 Target Size — every
interactive element ≥44×44px (exceeds the 24×24 minimum), per `.claude/rules/frontend.md`. 3.3.7
Redundant Entry — not applicable, no multi-step flow exists. 3.3.8 Accessible Authentication — the
login form allows paste (no JS blocking it) and works with password managers; TOTP entry accepts
paste of the 6-digit code.

### Verification

`tests/Feature/A11yTest.php` (authored in step 22, alongside the SEO audit — both are per-route
sweeps run once every public page exists) parses the rendered HTML of every published route with
Symfony's `DomCrawler` (already a transitive Laravel testing dependency — no new package) and asserts
structurally: exactly one `<h1>`, every `<img>` has a non-empty `alt` or `alt=""`, every `<input>`/
`<textarea>`/`<select>` has an associated `<label for>` or `aria-label`, a skip-to-content link is the
first focusable element, and no inline `style` attribute sets a color (proving §7's tokens are the
only color source). This is a real, mechanically-checkable subset of WCAG 2.2 AA — not a full
axe-core audit, which would require a headless browser this project does not otherwise depend on
(§18's `playwright-cli` stays optional).

```bash
./vendor/bin/pest tests/Feature/A11yTest.php   # DomCrawler structural sweep over every published route, expect: 0 failed
```

Manual passes before launch (post-build checklist, §20.4): one keyboard-only traversal of login → MFA
→ dashboard → publish a project → view it live; one screen-reader pass over the home and project-
detail pages; one 200%-zoom pass at 320px width. **These manual passes are where the properties a
static DOM sweep cannot see — actual contrast rendering, focus order, screen-reader announcement —
get their real coverage**, per §20.1's manual gate checklist.

## 16. Observability & Cost

### Instrumentation

| Signal | Tool | What it captures | Who looks at it |
|---|---|---|---|
| Errors | Laravel's default log channel (`stack`/`single`), `storage/logs/laravel.log` | Unhandled exceptions with stack traces, redacted of secrets | The owner, via SSH or a log-tail alias in `docs/runbook.md` |
| Logs | Same — structured single-line entries, one per request via the default request-id middleware | Request path, status, duration | The owner |
| Metrics | Horizon's own dashboard (`/horizon`, admin-authenticated) | Queue throughput, failed jobs, job latency | The owner |
| Uptime | External: a free-tier uptime monitor (e.g. UptimeRobot) polling `/health` every 5 minutes | Up/down, response time | The owner, via the monitor's own alerting |

No dedicated APM/error-tracking vendor (Sentry, Bugsnag) is added in v1 — a single-administrator site
with no paying users does not justify the account and the cost; `storage/logs/laravel.log` plus the
uptime monitor's alert is the whole v1 observability stack, and is recorded here as a deliberate
scope decision (§20.3), not an oversight.

### The metrics that matter for this project

| Metric | Target | Alert at |
|---|---|---|
| `/health` uptime | ≥99.5% monthly | any single check fails 3× in a row (external monitor) |
| Home page p95 response time (cached) | <200ms | >800ms sustained for 15 minutes |
| Horizon failed-job count | 0 | any job fails after its configured retries |
| Backup success (nightly `pg_dump`) | 100% of nights | any single night's backup script exits non-zero |

### Health check

`GET /health` (§5, step 24) — verifies a real `SELECT 1`, a real Redis `PING`, and
`migrate:status` reporting no pending migration. Polled by the external uptime monitor every 5
minutes; a `503` from any of the three checks is what actually pages the owner, not a bare `200`.

### Cost model

| Service | Free tier | Cost at v1 scale (1 admin, low public traffic) | Cost at 10× traffic | Cliff to watch |
|---|---|---|---|---|
| Proxmox LXC (self-hosted) | n/a — the user's own hardware | $0 marginal (sunk hardware/power cost) | $0 — traffic does not scale hardware cost until CPU/RAM saturates | Redis/Postgres memory pressure past ~4GB RAM (risk 6) |
| Cloudflare (DNS + proxy) | Free plan is sufficient | $0 | $0 | Free plan's rate limits, far above a portfolio site's traffic |
| Domain registration | n/a | ~$12/yr | ~$12/yr | none |
| Off-host backup storage | depends on provider | a few $/mo for tens of GB | linear with media library size | media library growth outpacing the LXC's own 30GB disk |
| Uptime monitor | Free tier (5-min interval) sufficient | $0 | $0 | none at this scale |

**Estimated monthly cost at launch: under $5** (domain amortized + backup storage), because hosting is
self-owned hardware. The cheapest lever if a cost line grows is media size — the medialibrary
conversion pipeline (WebP, step 23) already keeps stored images small; the escape hatch beyond that
is the S3 driver swap named as a non-goal trigger in §1.

### 20.2 Risk register

| Risk | Likelihood | Impact | Early signal | Mitigation |
|---|---|---|---|---|
| Content supply is the real bottleneck, not code | H | M | Launch with the demo seeder still live, or only 2–3 real projects filled in | Realistic seeder ships in step 12 so the build never blocks on copy; a separate tracked task (§20.4) replaces it with real content before public launch |
| Admin CRUD for 14+ entities sinks v1 if hand-built | M (mitigated) | H | Any step 14/15 estimate blowing past one sitting | Filament generates every resource (`--generate`), then it is edited — the single largest scope reduction in this design |
| Self-hosted deployment gets deferred to "later" and never happens | M | H | Step 5 slipping past the foundation epic | Deploy is Epic 01, steps 4–5, before any feature code exists — a hello-world reaches the real domain first |
| SVG upload is stored XSS | L (mitigated) | H | Any Filament upload field accepting `image/svg+xml` | SVG removed entirely from the allow-list (step 16); extension **and** sniffed MIME both checked |
| Single LXC is a single point of data loss | M | H | A restore drill that was written but never executed | Nightly `pg_dump` + media rsync **and** an executed restore drill with row-count assertions (step 24) |
| 4GB RAM is tight for Postgres + Redis + PHP-FPM + a queue worker on one LXC | M | M | `pm.max_children`/`shared_buffers` tuned wrong, OOM under load | Explicit tuning for the 4GB envelope in `infra/provision.sh` (step 4); monitored via `/health` and Horizon |
| A public admin login guarding a hiring artifact, with one account and no recovery path beyond codes | L (mitigated) | H | Owner loses both TOTP device and recovery codes | MFA mandatory, codes shown once and their storage documented in `docs/runbook.md`; residual risk **accepted on record** — there is no other recovery path in v1 |
| GitHub automation via PAT instead of `gh` (not installed on the build machine) | L | M | `scripts/github-bootstrap.sh` failing on an API shape change | Token-scoped narrowly (`Administration:write`, `Contents:write`, this repo only); step 2's assertions read back the actual protection state rather than trusting the request succeeded |

### 20.3 Decision log

| # | Decision | Rejected alternative | Why | Would reverse if |
|---|---|---|---|---|
| 1 | Laravel + Filament, overriding the marketing-site shape's TS/Astro default | Astro + a headless CMS | Content is admin-authored and database-driven, not files in a repo; the admin CMS is ~70% of the build and Filament generates it from Eloquent models | The admin surface shrinks to near-zero (e.g. content moves to files) |
| 2 | Filament over a hand-built admin | Custom Livewire CRUD screens | 14+ entities by hand is the single biggest scope risk this design found | Filament stops supporting a requirement this project needs (unlikely at these pins) |
| 3 | No Flux UI (free or Pro) | `livewire/flux-pro` | Not on Packagist (paid/private repo); the free tier is proprietary-licensed; neither is needed since Filament + bespoke Blade cover both surfaces | A future admin need genuinely requires a component neither Filament nor bespoke Blade can build reasonably |
| 4 | PostgreSQL over MySQL/SQLite | SQLite (viable per the runtime track for single-server apps) | The content is the irreplaceable asset; partial unique indexes and check constraints (§4) are used directly and need real enforcement | Never — SQLite's constraint model is a strict subset, this only gets truer over time |
| 5 | Mandatory TOTP MFA, not optional (overriding the source doc's §28) | Optional MFA | One account guards the whole hiring-facing artifact; the source doc's "optional" was written before that framing was explicit | Never — this is a security floor, not a preference |
| 6 | SVG removed from allowed uploads (overriding the source doc's §13) | Allow SVG, rely on MIME validation | MIME-type checking alone does not detect a script inside an SVG; stored XSS is the direct consequence | A sanitizing SVG pipeline (e.g. strip all `<script>`/event-handler content) is built and independently verified — not planned for v1 |
| 7 | No analytics vendor in v1 | Google Analytics / Plausible | No vendor means no cookie banner and no third-party script in the CSP; `NullAnalyticsProvider` keeps the seam open | Real traffic data becomes valuable enough to accept the privacy/CSP cost (§1 non-goal 11) |
| 8 | GitHub *content* import deferred to v1.1 | Build it now, alongside the dev-platform integration | It is unrelated to "GitHub as development platform," which is in v1 from step 2; conflating the two was identified as a real risk of scope confusion | The `PortfolioIntegration` seam (step 9) gets its first real consumer |
| 9 | No repository layer over Eloquent | A `Repository`/`Service` layer wrapping every model | The runtime track states explicitly this buys nothing at this scale; `app/Actions/` covers real domain logic | The team ever needs to swap the ORM itself (not anticipated) |
| 10 | Redis for cache/session/queue, no separate session store | Database session driver | Redis is already a required dependency for Horizon; adding a second store for sessions alone is unjustified | Redis becomes unavailable in the target hosting (not the case — it is provisioned in step 4) |
