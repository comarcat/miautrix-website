## 1. Project Overview & Non-Goals

### Vision

miautrix-website is a self-hosted professional IT portfolio, lightweight CMS, and personal blog for
a single IT infrastructure/project-management professional. One administrator manages every piece of
content — career history, projects, certifications, and blog articles — through a Filament admin
panel, with zero code edits required to publish or update content. Visitors get a fast, SEO-friendly,
professionally designed public site with two switchable visual themes (a restrained "Technical" theme
and an always-dark "Matrix" theme). The application is itself exhibited as a portfolio piece: its
architecture, CI/CD pipeline, security posture (mandatory MFA, hardened uploads, audit logging), and
deployment model to a single hardened Debian LXC are part of what the site demonstrates to the
recruiters and hiring managers who will read its source and visit its `/about` page.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|
| The administrator (site owner) | Publish/update career history, projects, certifications, skills, and blog articles via Filament; manage media, documents, and settings | Weekly, more during a job search |
| Recruiter / hiring manager | Skim experience, projects, and certifications; download the resume; judge technical credibility from the site itself | Once, occasionally revisits |
| Blog reader | Read technical articles, subscribe via RSS | Occasional, driven by search/social referral |

### Goals — v1 scope

1. The product lets the administrator manage every content type (career, projects, certifications, skills, media, documents, settings, blog) through Filament, with no code deploy required to publish.
2. The product presents a fast, accessible, SEO-optimized public portfolio and blog with two swappable visual themes sharing one component library.
3. The product enforces a hardened security posture appropriate to a public-facing single-admin system: mandatory TOTP MFA, rate-limited login, audit logging, hardened file uploads, and a tested backup/restore path.
4. The product deploys automatically via CI/CD to a single self-hosted Debian LXC, reachable at the real production domain over HTTPS from the earliest practical step.

### Non-Goals — explicitly out of scope for v1

| Not building | Why not now | Revisit when |
|---|---|---|
| LinkedIn import/export (either direction) | Two independent architect passes both flagged this as depending on an unversioned/unapproved external contract — either LinkedIn partner API approval (outbound share) or an unversioned export-file format (inbound). Same external-contract risk either way; not worth the v1 timeline. | v2, as export-file import only, admin-approved per row, no auto-share |
| GitHub content import (repo → portfolio project) | Distinct from GitHub-as-dev-platform (remote, Actions, branch protection), which IS in v1 from step 1. Deferred so this distinction is explicit and never conflated. The `PortfolioIntegration` interface and `imports`/`import_records` tables are created in v1 so the seam exists; nothing implements them yet. | v1.1 |
| Redis (queue/cache/session backend) | Laravel's database driver keeps the single Debian LXC to one service (Nginx + PHP-FPM + PostgreSQL). A supervised `queue:work` process replaces a Horizon dashboard — no queue UI in v1. | Queue volume or cache pressure genuinely exceeds what the database driver handles |
| More than two themes, or per-visitor theme creation | Two shared-component themes are already real scope (every component styled twice, one theme with its own always-dark contrast rules). A third multiplies that surface for a single-admin site with no evidence of demand. | A concrete visitor request or a rebrand |
| Comments or multi-author blog | Single administrator; no moderation capacity or need. | A co-author or guest-post need appears |
| Public JSON API | No consumer for one in v1; the public site is server-rendered Blade. | A concrete integration (e.g. a future mobile client) needs one |
| Multi-language site | No stated audience need; doubles every content field and template. | A demonstrated bilingual audience |
| Dynamic PDF resume generation | Uploading versioned PDFs is simpler and matches how a resume is actually authored and re-used elsewhere. | A recruiter-facing need for tailored resume variants |
| Complex RBAC / multiple administrators | roles/permissions tables are installed and a single `super_admin` is seeded; additive design means more roles can be added later without a schema migration risk. | A second administrator (e.g. a co-maintainer) is actually onboarded |
| Global full-text search | No content volume in v1 that search meaningfully improves over browsing/filtering. | Article/project count grows past what a category filter can handle |
| S3 or other object storage | Local disk keeps the single-LXC deployment simple; the media disk is swappable later via Laravel's filesystem abstraction. | The LXC's local disk becomes a real capacity constraint |
| Analytics vendor integration | `AnalyticsProviderInterface` is defined as a null implementation; no cookie banner is needed because nothing tracks visitors in v1. | A concrete analytics need that justifies the cookie-consent surface |

**The builder must not implement anything in this table**, even if it seems like a small addition
while working on an adjacent step. If a step appears to require a non-goal, that is a blueprint
defect — stop and report it rather than expanding scope.

|---|---|---|
| Language / runtime | PHP ^8.4 (8.5.10 installed) | Not laravel/framework's floor — `pestphp/pest@5.1.3` requires PHP `^8.4`, which is the actual hard floor for this stack |
| Framework | laravel/framework ^13.30 | Batteries-included: routing, Eloquent, migrations, mail, jobs, cache, admin ecosystem (Filament) — beats assembling the same from a dozen npm packages for a content-driven, admin-authored site |

| Styling | Tailwind CSS ^4.3.3 + `@tailwindcss/vite` | Utility-first, token-driven via `@theme`, no runtime CSS-in-JS to fight Livewire's server-rendered model |
| Component layer | One shared Blade component library (Button, Card, Badge, Timeline, Table, Tabs, Modal, Alert, Toast, FileUpload, ImageGallery, Breadcrumb) | Two visual themes must never mean two component trees — this is Risk #8's mitigation |
| Database | PostgreSQL 18 | Relational integrity for career/project/blog data with real foreign keys; single-LXC-friendly; no document/relational mismatch |
| ORM / data access | Eloquent directly, no repository layer | `app/Actions/` for domain logic, `app/Services/` reserved for external clients (none in this scope) — a repository layer over Eloquent buys nothing per the runtime track's own guidance |
| Auth | laravel/fortify ^1.39, native TOTP two-factor | Headless auth backend with built-in `TwoFactorAuthenticatable` — no extra MFA package needed; MFA is mandatory (Risk #6), not optional |
| Background work | Laravel database queue driver, `queue:work` under supervisor | No Redis (Non-Goal #3) — a single low-traffic LXC does not need a second service; supervised `queue:work` replaces Horizon's dashboard |
| Payments | NOT APPLICABLE — no payment surface in v1 | — |
| File storage | Local disk, outside web root, served through a controller | S3 deferred (Non-Goal); hardened upload validation removes SVG entirely (Risk #4) |
| Email / notifications | Laravel Mail (SMTP, provider TBD by administrator at deploy time) | Standard Laravel mailer; used for contact-form relay and Fortify password reset |
| Hosting | Self-managed Debian 13 "trixie" LXC: Nginx + PHP-FPM + PostgreSQL + supervisor | Single point of control for a portfolio piece that exhibits its own deployment model (Risk #3); no vendor lock-in narrative for a portfolio site |
| Package manager | Composer (PHP) + npm (JS/Vite) | From the runtime track; standard Laravel toolchain |

### Compatibility check

Checked against `knowledge/stack-compatibility.md` — no known-bad combinations apply. Specifically
confirmed: this project uses exactly one identity provider (Fortify — no second auth library or
hosted IdP), one styling paradigm (Tailwind utility CSS — no runtime CSS-in-JS), one migration system
(Laravel migrations — no dashboard schema editor), a pooled-appropriate direct PostgreSQL connection

(Filament 5.7.8 requires livewire/livewire `^4.1`; pinned 4.4.3 satisfies it — both move together on
the 4.x line only, stated explicitly in §11 and in `workspace/CLAUDE.md`).

**Boundary rules**
- `app/Http/Controllers/` never queries Eloquent directly for anything beyond a simple `find`/`with` —
  non-trivial domain logic lives in `app/Actions/`.
- `app/Services/` is reserved for external API clients; it stays empty in v1 (no external clients —
  LinkedIn/GitHub-import are deferred). Do not put domain logic there.
- Both themes share the Blade components under `resources/views/components/` and `app/View/Components/`
  — there is never a `themes/technical/` and `themes/matrix/` component tree. Only tokens differ,
  switched by the `data-theme` attribute on `<html>`.
- SoftwareProject is a relation manager on `ProjectResource` (Filament), never a standalone
  `app/Filament/Resources/SoftwareProjectResource.php` file.
- Media and documents are stored under `storage/app/private-media/`, outside `public/`, and are only
  ever served through `app/Http/Controllers/Public/MediaController.php` (step 16) — never via a
  public symlink.

This project states one resolution convention: PHP namespaces follow PSR-4 exactly as `composer.json`
declares (`App\` → `app/`), and Blade view names follow dot-notation matching the `resources/views/`
tree (`public.home` → `resources/views/public/home.blade.php`). See §19.6's *Resolution convention
matrix* for how this is verified across application code, Pest tests, and Artisan console commands —
the three loaders in a Laravel project.

No output path in this tree is contested between two configs: the Vite build output directory
(`public/build/`) is declared once, in `vite.config.js` (authored by the `laravel new --livewire`
scaffold, step 1) and referenced by `resources/views/layouts/app.blade.php`'s `@vite` directive. See
§19.6's *Cross-artifact value reconciliation* table.

### Relationships

- `profiles` 1—(N)→ `experiences`, `education`, `certifications`, `skills`, `social_profiles`. Cascade: delete profile → soft-delete children (app-enforced in the Action, not a DB cascade, so soft-deletes are preserved).
- `companies` 1—(N)→ `experiences`. On company hard-delete: blocked while any non-deleted `experience` references it.
- `projects` N—(1)→ `project_categories` (nullable). N—(N)→ `technologies`, `media` (via pivots), `documents` (via pivot). `projects` 1—(1)→ `software_projects` (extension, cascade delete on the extension row when the parent project is force-deleted).
- `skill_categories` 1—(N)→ `skills`.
- `documents`, `certifications`, `media` avatar/logo/badge references are foreign keys with `nullOnDelete` — losing a media row degrades gracefully to no image, never a broken foreign key.
- `imports` 1—(N)→ `import_records`. Unpopulated in v1.
- `audit_logs` has no outgoing FK cascade — `user_id` is `nullOnDelete` so history survives a deleted user.

### Migrations

Laravel migrations, one file per logical change, run with `php artisan migrate`. Naming: the
timestamp prefix Laravel's `make:migration` generates — never hand-invented. Production migrations
follow expand-then-contract: an added column is nullable first, backfilled, then made `NOT NULL` in a
follow-up migration; a destructive migration (dropping a column) never ships in the same deploy as the
code that stops using it. `migrate:fresh` and `db:wipe` are never used outside local development —
enforced by a grep guard in step 27's deploy script.

### Rendering strategy

Every public route is server-rendered Blade (no client-side routing, no SPA). Pages render fully on
the request; there is no ISR/ISG concept in Laravel — instead, step 26 adds database-driven page
caching keyed by route + query string, invalidated explicitly on publish/unpublish of the owning
entity (a Filament model-event listener clears the relevant cache key). Livewire components
(theme switcher, contact form) hydrate client-side after the initial full HTML paint, so the
`data-theme` attribute is correct on first paint with no flash (persisted via cookie, read
server-side in the base layout).

### Component hierarchy

```
layouts/app.blade.php                 # <html data-theme="{{ $theme }}">, meta component, header, footer
  components/theme-switcher.blade.php # Alpine + Livewire-free cookie toggle (client JS writes cookie, page reloads to re-render server-side)
  public/home.blade.php
    components/card.blade.php
    components/badge.blade.php
    components/timeline.blade.php
  public/projects/show.blade.php
    components/image-gallery.blade.php
    components/tabs.blade.php
  livewire/contact-form.blade.php     # the one genuinely interactive public surface (Livewire, validated server-side)
```

### State management

Server state only — every page reads directly from Eloquent on each request; there is no client-side
data-fetching layer. The one piece of client state is the current theme, held in a cookie
(`miautrix_theme`, values `technical` or `matrix`) read server-side by
`app/Http/Middleware/ResolveTheme.php` and exposed to the layout as `$theme`. Livewire component
state (contact form) is server-authoritative between requests; nothing public-facing uses a global
JS store.

### Loading, empty, and error states

- **Projects/Certifications/Blog index with zero published rows**: renders a designed empty state
  ("No projects published yet" + an icon), never a blank page or a broken loop — this is Risk #1's
  concrete UI mitigation, verified by the seeder guaranteeing this never actually happens in the
  shipped v1 but the template still handles it defensively.
- **Contact form submit**: Livewire `wire:loading` state disables the submit button and shows a
  spinner; success shows an inline confirmation; validation errors render inline near each field
  (never a top-of-page-only banner — accessibility requirement, §15).
- **Media/document 404**: a styled 404 page, not the framework default, for any unpublished or
  missing media/document request.

## 8. Authentication & Authorization

### Provider and rationale

laravel/fortify `^1.39`, headless auth backend, with **native TOTP two-factor** (Fortify's own
`TwoFactorAuthenticatable` trait + `EnableTwoFactorAuthentication` action) — no extra MFA package.
One identity provider only, per `stack-compatibility.md`'s known-bad-combination rule (never two).

### Flows

- **Sign-in** → email + password → **MFA challenge is mandatory** (Risk #6): if
  `two_factor_confirmed_at` is null, redirect to forced enrolment (QR code + recovery codes shown
  **once**) before any dashboard access; if confirmed, prompt for a TOTP code or a recovery code.
- **Password reset**: standard Fortify flow (email link, one-time token, expires in 60 minutes).
- **Session expiry**: idle timeout 120 minutes, absolute session lifetime 8 hours, enforced via
  Laravel's session `lifetime` config plus a last-activity middleware.
- **Sign-out**: invalidates the session and regenerates the CSRF token.
- **Account deletion**: NOT APPLICABLE — a single seeded `super_admin`, no self-service account
  deletion flow in v1 (Non-Goal #9, complex RBAC deferred).
- **Failure branches**: 5 failed login attempts per email+IP in 15 minutes → 429 with a named
  rate-limit message (login audit logging records every attempt, success or failure, per Risk #6).

### Route protection

| Surface | Rule | Enforced where |
|---|---|---|
| `/admin/*` | authenticated + `super_admin` role + `two_factor_confirmed_at` not null | `app/Http/Middleware/EnsureMfaConfirmed.php`, applied in the Filament panel provider (step 13) |
| Filament resource actions (create/edit/delete) | Policy per model | `app/Policies/*Policy.php` (step 11), registered via `AuthServiceProvider` |
| `/media/{media}/...`, `/documents/{document}/download` | public only if the owning entity is `published = true` | the media controller's own query scope (step 16) |

**Enforcement rule:** authorization is checked server-side on every request, in the Policy or the
controller/Action — never only by hiding a Filament navigation item.

### Roles and permissions

| Role | Can | Cannot |
|---|---|---|
| `super_admin` (single seeded user) | Full CRUD on every content model, view audit logs, manage settings | Nothing is restricted — the only role in v1 |

Additive design: `spatie/laravel-permission`'s tables are installed and Policies check permissions,
not a hardcoded role check, so a second role can be added later (Non-Goal #9) purely by data, without
a schema migration.

### Sessions

Database session driver (Non-Goal #3 — no Redis), `HttpOnly`, `Secure` (production only, via
`SESSION_SECURE_COOKIE=true`), `SameSite=Lax` cookies. CSRF via Laravel's standard
`VerifyCsrfToken` middleware on every state-changing request (web routes and Livewire's own CSRF
handling).

### Multi-tenancy / row-level isolation

NOT APPLICABLE — single administrator, no tenant boundary. Every content model belongs to the one
application, not to a user-scoped tenant.

### Bootstrap

```bash
# order matters: ignore file + exceptions -> repo init -> first commit -> install -> services -> migrate -> seed

# 1. Repository init is idempotent — the target already has one commit from a prior blueprint's
#    Bootstrap run, so this is a no-op here, but every future re-run of this block must not assume that.
git rev-parse --git-dir >/dev/null 2>&1 || git init -b main

# 2. Copy the agent workspace + every verify-critical config INTO the project root, non-clobbering.
#    rsync -a --ignore-existing: skips any file already present (e.g. this repo's existing composer.json
#    once step 1 has run), and exits 0 whether it copies or skips — unlike `cp -Rn`, which exits 1 on
#    BSD/macOS when it skips a file, which would abort this block under `set -e` on a second run.
#    Never overwritten by this line once present: composer.json, package.json, composer.lock, package-lock.json —
#    none of those are emitted under workspace/ in the first place (see §2's manifest ruling), so the
#    guard's real job here is protecting phpstan.neon/pint.json/.env.example/docker-compose.yml/ci.yml/
#    tests/TestCase.php/.claude/** from being clobbered by a second run after they have been hand-edited.
rsync -a --ignore-existing workspace/. ./

# 3. The ignore file (Laravel's default, already carrying the `!.env.example` and `.claude/` exceptions
#    from the "Files that must be committed" table above) is now in place. Make the first commit.
git add -A && git commit -m "chore: scaffold" --allow-empty

# 4. Approve project CLIs non-interactively where the tool supports it; `laravel new` (step 1) is
#    interactive by default for the starter-kit prompt — the actual step 1 Do block passes
#    --livewire --pest explicitly to skip that prompt entirely.

# 5. Start local services (Postgres 18 only — no Redis).
docker compose up -d
sleep 2
docker compose exec -T postgres pg_isready -U miautrix   # confirm ready before the next command

# 6. Install PHP + JS dependencies (step 1 has already run `laravel new`, composer.json exists by then;
#    this Bootstrap re-run form is what a stuck builder invokes after step 1).
composer install
npm install

# 7. Migrate and seed.
php artisan migrate
php artisan db:seed
```

**Every command above is safe to run twice.** The `git init` line is guarded, the `rsync` copy is
non-clobbering and exits 0 either way, `docker compose up -d` is idempotent, `composer install`/
`npm install` are idempotent by design, and `migrate`/`db:seed` are guarded by Laravel's own
migration-tracking table (re-running `migrate` on an already-migrated database is a documented no-op;
re-running `db:seed` is intentionally **not** idempotent for row counts, so the build order runs it
exactly once, in step 12, and Bootstrap's own listing above is the from-clone path, not a
repeat-every-session command).

This block is executed, verbatim, in a scratch checkout before this blueprint is presented, per the
generation procedure. If any line here fails, hangs on a prompt, or leaves the directory in a state
step 1 cannot use, that comes back as a finding rather than being discovered by the eventual builder.

## 12. Deployment Strategy

### Hosting

A single self-managed Debian 13 "trixie" LXC (container or lightweight VM, provider-agnostic —
Proxmox, a bare VPS, or any LXC-capable host) running Nginx (reverse proxy + static assets),
PHP-FPM 8.4+, PostgreSQL 18 (bound to `127.0.0.1`), and `supervisor` (the queue worker). This is a
deliberate exhibit of the administrator's own infrastructure/project-management specialty — one
deployable unit, no managed-PaaS abstraction hiding the architecture from a visiting recruiter who
reads the source. Build command: `npm run build` (Vite, output to `public/build/`). Runtime setting:
PHP-FPM pool `pm = dynamic`, `pm.max_children` sized to the LXC's RAM (documented in
`infra/provision.sh`'s comments, not repeated here as a number that would drift).

### Environments

| Environment | Branch | URL | Database | Third-party mode |
|---|---|---|---|---|
| Local | — | `http://localhost:8123` (via `php artisan serve`) or `http://localhost` (via `docker compose`) | local `docker-compose.yml` Postgres | test SMTP (Mailpit or log driver) |
| CI | any pushed branch / PR | N/A (ephemeral) | GitHub Actions Postgres 18 service container | no third-party calls |
| Production | `main` | the production domain (Cloudflare-proxied) | the LXC's local PostgreSQL 18 | live SMTP credentials |

### CI/CD

1. Checkout, set up PHP 8.4 + Node 24.
2. `composer install`, **`composer audit`**.
3. `./vendor/bin/pint --test`, `./vendor/bin/phpstan analyse`.
4. `php artisan migrate --force` against the Postgres 18 service container.
5. `./vendor/bin/pest --ci`.
6. `npm ci`, **`npm audit --audit-level=high`**, `npm run build`.
7. On `main` only, after all of the above pass: SSH to the LXC and run `infra/deploy.sh`.

This is the same gate set as §20.1 — every check in the acceptance gate runs in CI, no exceptions.

### Release and rollback

`infra/deploy.sh` (step 27) does: `git pull`, `composer install --no-dev`, `npm ci && npm run build`,
`config:cache route:cache view:cache`, `php artisan migrate --force`, restart the `queue-worker`
supervisor program. Migrations follow expand-then-contract (§4) so a code rollback (`git checkout` to
the previous release tag + re-run the cache/restart steps, skipping `migrate --force`) never needs a
matching down-migration in the same deploy. A bad deploy is reverted by checking out the previous
`step-*`/release tag and re-running the non-migration parts of `deploy.sh`; typical rollback time is
under two minutes (asset rebuild dominates).

### Domain, DNS, TLS

An `A` record for the apex/subdomain pointed at the LXC's public IP, proxied through Cloudflare
(orange-cloud) for TLS termination at the edge and DDoS mitigation. Origin traffic uses Cloudflare
Origin CA certificates on Nginx. `http://` requests 301-redirect to `https://` at Nginx. No apex↔www
redirect is needed — the site is single-domain, no `www.` variant is provisioned.

### Critical flows to cover Feature-level

1. Admin login → MFA enrolment/challenge → publish a new Article → article appears on `/blog` and in `/feed.xml`.
2. A visitor submits the contact form with a filled honeypot → silently discarded, no mail sent.
3. An unpublished entity's slug is requested directly → 404, and its media is not servable via `/media/...`.

### Test data

A dedicated test database (`miautrix_test`) runs against the same `docker-compose.yml` Postgres 18
service used for local dev (a second logical database on the same container, `TEST_DATABASE_URL` in
§10), reset via Laravel's `RefreshDatabase` Pest trait (migrate fresh per test class, wrapped in a
transaction per test — this is the one legitimate use of a fresh-schema operation, confined to the
test runner, never to `infra/deploy.sh`). CI uses its own ephemeral Postgres 18 service container,
migrated fresh per run. Tests never share mutable state and never depend on execution order (Pest's
default parallel-safe isolation via `RefreshDatabase`).

### What is deliberately not tested

- Visual pixel-perfection of the design tokens — covered by the a11y structural sweep and the
  Lighthouse/manual render checks (§7, §15), not by snapshot-diffing rendered pixels.
- The deferred `PortfolioIntegration`/`imports` seam — it has no implementation in v1 (Non-Goal #2),
  so there is nothing behavioral to test yet beyond the schema tests in step 9.
- Load/stress testing — out of scope for a single-administrator portfolio site at v1 traffic levels.

#### A resolution convention is decided once and reconciled against every loader

**The convention, stated once:** PHP namespaces resolve via Composer's PSR-4 autoloader
(`App\` → `app/`, declared in `composer.json`'s `autoload.psr-4`, authored by `laravel new` in step 1
and never hand-edited); Blade view names resolve via dot-notation against `resources/views/`
(`public.home` → `resources/views/public/home.blade.php`), which is Laravel's own view-finder
convention, not something this blueprint configures separately.

#### Resolution convention matrix

| Context | Command that exercises it | Convention as it appears there | Config + literal setting that makes it work |
|---|---|---|---|
| Application source | `php artisan serve` / `php-fpm` | `App\Models\Project` resolves to `app/Models/Project.php` | `composer.json` — `"autoload": {"psr-4": {"App\\": "app/"}}`, authored by `laravel new` |
| Test files (Pest) | `./vendor/bin/pest` | Same PSR-4 autoload, loaded via Composer's autoloader which `tests/TestCase.php`'s bootstrap requires | `composer.json`'s `autoload-dev.psr-4` maps `Tests\\` → `tests/`, also authored by `laravel new`; `phpunit.xml`'s `bootstrap="vendor/autoload.php"` attribute is what loads it |
| Standalone scripts (`php artisan seo:audit`, `php artisan tinker`) | `php artisan seo:audit`, `php artisan tinker --execute=...` | Same PSR-4 autoload — `artisan` itself bootstraps the full framework, so there is no "bare runtime" divergence in this stack (unlike a Node/TS project, Artisan commands always load the Composer autoloader and the full container) | `bootstrap/app.php` (Laravel's own bootstrap, unmodified) |
| Build (Vite) | `npm run build` | JS module resolution is separate from PHP's PSR-4 — `resources/js/app.js` imports Alpine via its npm package name, resolved by Vite/Node's own `node_modules` resolution, not PSR-4 | `vite.config.js`, authored by `laravel new --livewire`'s scaffold with the Tailwind v4 plugin added in step 1 |

Because every PHP-side loader in this stack (the running app, Artisan commands, and Pest) all load
through the **same** Composer autoloader with **no** bundler-only entry points, export conditions, or
ESM/CJS boundary (Laravel does not have Node's dual-module problem on the PHP side), this convention
has no context-specific divergence to reconcile — a genuine case where "works by default" is honest,
because the resolver is the same one PHP process in every row above. The one place this stack *does*
have a second resolver (Vite/Node for JS assets) uses an entirely separate module system (npm/ESM)
with no naming overlap with the PSR-4 convention, so there is no cross-contamination to check.
